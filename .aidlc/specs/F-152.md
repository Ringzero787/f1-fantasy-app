# F-152 — UC: auto-retry held results and resolve unknown cars by name

Created: 2026-11-15 · Status: implemented

## Goal

Both 2026 holds were a car number the driver table did not know: Mexico City (car 50, Hirakawa
standing in for Ocon, F-134) and São Paulo (car 51, Câmara, whom F-138 had put in car 50, F-139).
Each race was fetched on time and then sat unscored until a code change was deployed and the race
re-queued by an op; São Paulo for three days, noticed by the owner. Players saw no score. Now the
ingestion resolves such a car from the provider's own entry list, and a race that is still held is
fetched again by itself, so neither weekend would have needed anyone. Owner decision 2026-11-15:
retry and resolve by name (over retry only, or retry plus an alert).

## Acceptance criteria
- [x] `functions/src/ingestion/resolveCars.ts` `resolveUnknownCars(entries, roster, warnings)` (pure): for a car the table does not know, a `drivers/` doc whose three-letter code AND surname (accents and case ignored) both match the session's entry record is credited under its id (São Paulo: car 97/51 → `camara`); a name that matches no doc is a stand-in under its surname with no `drivers/` doc, so nobody can buy him (Mexico City); the table's own stand-in id (no doc) is the same driver back in another car.
- [x] Refused, so the race holds as before: code matches but surname does not (or the reverse), two docs sharing the code, a stand-in surname that is another driver's id, two cars resolving to one id, a car resolving to a driver the table seats in another car of the session, a record without a code or a name, a stand-in id that is a constructor id (Haas, Williams…) or a built-in object name. Known numbers are never re-resolved. Any race, qualifying or sprint result that credits one driver in two cars (an entry list that leaves out the car the table gives him) is held (`duplicateDriverWarnings`, unmapped prefix).
- [x] Race, qualifying and sprint converters, the starting grid and the fastest lap all use the resolution (the grid and lap rows carry only a number, so the race session's resolution is passed to them). Without a roster the converters behave exactly as before (the Zandvoort rule test still holds the same weekend).
- [x] Every resolution is a warning prefixed `Resolved by name` on the pending result, naming the car, the id and how; the hourly ops check WARNs on any race scored that way in the last 7 days ("add it to DRIVER_NUMBER_TO_ID").
- [x] A result held on a `blockedReason` is fetched again every 30 minutes (`HELD_RETRY_MS`) for 14 days after the race (`HELD_RETRY_FOR_MS`, pure `heldAction`; each attempt stamps `retriedAt`, so a retry that ends early still waits 30 minutes, and a minute's slack keeps it off the 40th), and scores once every car resolves (a mapping deployed, or the provider completing its entry list); no re-queue op. A pending result without a reason still waits for an admin; past 14 days `requeueBlockedResults.js` is the way back. The ops check's held-race FAIL says so, and names the re-queue op once the race is past the 14 days or completed. A failed entry-list fetch fails the attempt (retried), never scores without the grid and fastest lap of a resolved car.
- [x] Tests: functions 300/300 (`resolveCars.test.js` +9, incl. the converters over a stubbed São Paulo-like feed with a stand-in, and the duplicate hold), scripts 207/207 (+2).
- [x] Proved on real data (read-only: provider entry lists, production `drivers/`): with the hand mappings removed in memory, Mexico City car 50 → `hirakawa`, São Paulo car 51 → `camara`, Zandvoort car 22 → `tsunoda`; with the table as it is, all 50 completed 2026 race, qualifying and sprint sessions resolve nothing and warn nothing.

## Targets
- server: Cloud Functions checkOpenF1Results, checkQualifyingResults, checkSprintResults (functions deploy). `moonshotLiveSweep` imports the client but is unchanged in behaviour (no roster passed).
- ops: `scripts/ops/pitwall-check.js` and `pitwall-check-lib.js` (cron runs the repo file; no deploy).

## Data
No user data. Reads the `drivers` collection (id, name, shortName) once per checker tick.

## Performance budget
One `drivers` read (about 25 documents) per checker tick that has a race or session to fetch, plus one extra `/drivers` call per race fetch; a held race costs one fetch per 30 minutes instead of none.

## Out of scope
- A known number whose car changed hands to another driver (the table credits the old occupant; only SHARED_NUMBERS numbers check the name). Same risk as today, not widened.
- The Moonshot live sweep during a race does not resolve unknown cars (Moonshots settle in the scoring run, which does).
- Creating `drivers/` docs or prices for a resolved stand-in; a permanent replacement still goes through setDriverSeat.js.
- Track Limits reads the same `races` results: a resolved stand-in reaches it under his surname id, as Hirakawa (`hirakawa`) did at Mexico City.
