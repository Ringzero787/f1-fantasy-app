# F-118 — UC: a team created after the lock sweep is still locked for that race

Created: 2026-10-09 · Status: building · Design source: recorded as open in `.aidlc/specs/F-098.md`
("a team created after the sweep is never locked (roster included, the bigger half)") and raised
again on 2026-10-09 with Singapore 56h away

## Goal
Undercut (server + rules). `autoLockTeams` only looks at races still `upcoming`, and locking a
weekend is what flips that race to `in_progress` — so the sweep never comes back to it. A team
created from that moment until the race is scored was never locked and never stamped with an ace
window. Its roster stayed editable through the sprint and the race (the roster callables check only
the team's own `isLocked`), and `aceIsFrozen` found no window to compare `request.time` against, so
its ace did too. That is the hole F-095 and F-098 closed for every team the sweep did reach, left
open for anyone who joined mid-weekend. This closes it, and fixes the related case where a league's
roster deadline decided whether the ace was frozen at all.

## Acceptance criteria
- [x] **The ace window has exactly one definition.** `aceWindowFor(raceId, race)` in
      `functions/src/utils/lockTime.ts`, used by the sweep and by `createTeamSecure`. Two copies of
      this arithmetic would diverge, and a deadline one writer knew about and another did not is
      precisely how F-095 and F-098 went wrong. It returns **null** when the race has no usable
      start, because a window with no end is F-095's rejected shape; the sweep skips stamping
      rather than stamping something open-ended (tests).
- [x] **The window never consults the league's `lockDeadline`.** The ace locks at lights out and
      starts scoring at the first session it doubles, both from the race schedule. Keying it off
      the roster deadline is why a `lockDeadline: 'race'` league got **no freeze at all** — those
      players could watch the sprint and the race and move the ace throughout. The sweep now stamps
      every team the weekend covers whatever the deadline says. **0 of 24 leagues are configured
      that way (2026-10-09), so this was latent, not live.**
- [x] **`config/lockState` publishes the live weekend at a fixed path**, written by the sweep
      immediately before the race flips out of `upcoming`, so there is no instant where the sweep
      has moved on and the rules cannot yet tell. Rules cannot run a query and cannot derive the
      live race id, so one document at a known path is the only thing they can read. It carries its
      own `aceLockUntil` (race + 24h) and so **expires on its own**, and Phase 5 of scoring deletes
      it — but only when `raceId` matches, because another weekend's marker is not ours to delete
      and deleting the wrong one would unfreeze live aces.
- [x] **The ace of an unswept team is frozen by the live weekend** (`aceFrozenByLiveWeekend` in
      `firestore.rules`, five `let`s — the ceiling is ten). Covered by rules tests: frozen for
      driver and constructor ace; free with no marker; free before the marker's `aceFreezeFrom`;
      free once the marker is past its ceiling; and a forged `lockStatus` is no escape, since it is
      a denied key. **The two freezing cases fail against the previous rules** — checked.
- [x] **The roster of an unswept team is refused mid-weekend**, in
      `assertOwnedUnlockedTeam`, which all five roster callables go through.
- [x] **The deliberate F-098 gap survives.** This is why the gate is the *stamped window* and not
      "is a weekend live": a swept team's ace reopens once the sessions it doubles have been scored,
      between qualifying and lights out, and a blanket weekend freeze would have taken that from
      every player. A swept team carries this weekend's stamp, so `aceIsFrozen` remains the single
      authority on it, gap included. The rules test for this **fails against a blanket freeze** —
      checked by removing the stamp comparison.
      **Correction:** an earlier draft of this spec justified the design by saying `earlyUnlockTeam`
      is a paid way to edit a roster mid-weekend that a weekend-wide refusal would have broken.
      That is wrong — `earlyUnlockTeam` refuses outright while a weekend is live (F-095 made it ask
      the race calendar); it buys a way out of the **season** lock. During a live weekend an
      unlocked team is essentially always one the sweep never reached. The stamp is still the right
      test, for the gap above and because it is the one thing a forged payload cannot fake.
- [x] **No client can write `config/lockState`, admin claim included.** It *is* the ace freeze for
      every unswept team, so a hand-write unfreezes all of them mid-race — or freezes everyone's.
      `config/{docId}` granted write to an admin custom claim; `lockState` is now excluded from it.
      Nothing legitimate loses anything: the sweep writes it and scoring deletes it, both through
      the Admin SDK, which does not consult these rules at all. Note Firestore grants on **any**
      matching rule, so this had to be an exclusion in the existing block rather than a stricter
      `match /config/lockState`, which would merely have been additive. Reads are untouched. Tested,
      and the test fails without the exclusion.
- [x] **`createTeamSecure` creates a mid-weekend team locked and stamped**, so every mechanism that
      already exists works unchanged rather than needing a new one.

- [x] **The roster gate is a pure function with executable tests.** `stampedForWeekend` in
      `functions/src/locks/lockState.ts`, so it can be exercised without a Firestore fake this repo
      does not have. Covered: no live weekend; this weekend's stamp (including a different object
      with the same instant, since the sweep and the marker are separate writes); an unswept team;
      and the forged and stale stamps the security read got past the first version in the emulator
      — `'x'`, a number, last month's timestamp, and an object whose `toMillis` is not a function.
      One test asserts the two halves agree: what `createTeamSecure` writes for a mid-weekend team
      passes the gate the roster callables apply, or a player would be locked out of their own
      brand-new team.

## Deliberately NOT done: gating team creation in the rules
The obvious fix — require a client-created team to arrive locked with the window — **was rejected
after checking who actually creates teams.** No client calls `createTeamSecure`: every build,
including 2.5.1, goes through `teamService.createTeam` → `addDoc` (`src/services/team.service.ts`),
and that payload has no ace fields at all. A rule requiring them would break team creation
mid-weekend for **every shipped build**, including the one released today, for a `permission-denied`
nobody could act on. So the mutations are gated instead and creation is left alone. The callable
change is defence for the day a client does use it, not the live path.

## Targets
- firebase (functions: the sweep, scoring Phase 5, the team callables; rules)
- No app build. Nothing here is native or client-side, which is why it can deploy without one.

## Data
One new document, `config/lockState`: a race id, a lock timestamp and the five ace-window fields —
all derived from the race schedule, no personal data. Read by `firestore.rules` through `get()`,
which is not itself rule-governed. Teams gain no new fields; the ace window keys are the ones
F-095/F-098 already defined.

## Still open
- **The roster gate is advisory, by design.** `liveLockState` is read outside the transaction, so a
  roster edit committed in the milliseconds between the sweep publishing `config/lockState` and
  writing the team's own lock could slip through. The authoritative state remains the team's own
  `isLocked`, which the same sweep sets.
- **A `lockDeadline: 'race'` league's roster still never locks.** Only its ace window is fixed here.
  Locking those rosters needs a second sweep phase at lights out, because the race is already
  `in_progress` by then and `dueRaces` only considers `upcoming`. No league uses that setting.
- **A mid-weekend team is not auto-filled.** Teams present at the sweep get value auto-fill (F-044);
  one created afterwards is locked with an empty roster and scores nothing that race. That is the
  honest outcome rather than letting them pick with the sessions run, but offering them the next
  race instead would be kinder, and `joinedAtRace` is client-side display only — scoring never
  reads it.
