# F-129 — UC: Race-day running score from live positions

Created: 2026-10-26 · Status: implemented, unreleased (inert until the live-timing switch) · From the
owner after F-128 landed: "can we now do anything with live timing now it works? as in pulse updates
on points and show a projection on the tile or something?"

## Goal
Undercut, server + app. With F-128 the live sweep (F-111) can read the timing feed during a race.
Today it writes only positions, for the Moonshot card. This feature makes the same once-a-minute
document carry a **running score** — what every driver and constructor would score for the race
session at the current running order — and shows it on the Team screen: each tile's trend corner
becomes a pulsing `LIVE +N` and the LAST RACE stat becomes `LIVE · SO FAR` with the roster's total,
for the three hours of the race. Nothing on the device talks to the provider; nothing is computed
on the device beyond multiplying the Ace and summing the roster.

It is a running score, not a result or a forecast (F-070's projections are the pre-race forecast
and are untouched). Qualifying and sprint points are already banked on Saturday; the loyalty lock
bonus is added at settlement; a retired car has no flag in the positions feed. What the feed does
with one was checked on the 2026 United States race (session 11396): all three retirements moved
to P20–P22 within seconds of stopping and no two cars ever shared a final position, so a stopped
car sits at the back of the order and is scored as a finisher there until the official
classification applies the real penalty. The copy never says "points scored" or "result".

## Acceptance criteria
- [x] **Pure running score** (`functions/src/scoring/runningScore.ts`): per driver, exactly what
      `calculateDriverPoints` gives a classified finisher at that position (race points, places
      gained or lost against the grid, fastest lap inside the top ten, reverse-grid bonus), with
      `racesHeld 0` and no Ace; per constructor, `constructorRacePoints` (new in scoringCore, the one place the team formula lives) summed over its cars: position points + reverse-grid bonus,
      the constructor scorer's formula. An empty grid credits nobody with places; a known grid
      missing a car starts it from the back (22), as the official scorer does. Tests:
      `functions/test/runningScore.test.js` (equality with `calculateDriverPoints`, fastest lap
      top-ten only, grid absent / partial, constructor sums, skipped bad positions, the retired-car
      limit stated as a test).
- [x] **The sweep carries it** (`functions/src/moonshot/liveSweep.ts`): once per race it also
      fetches the starting grid from the provider's `/starting_grid` only (never the qualifying
      classification the results ingest falls back to: a qualifying order fetched half an hour
      early would be kept all race and misstate places gained for every penalised or pit-lane
      starter; it is asked again each minute until published) and the entry list (driver → constructor, through the same team-name
      table the results ingest uses) and keeps both in the document; each minute it fetches the
      laps for the fastest lap. A failed grid, entry-list or laps call never stops the positions
      from being written: that minute's score simply has no places, and the last known
      fastest-lap holder stands (a fastest lap so far can move, never vanish). Every feed call
      is bounded at 20 s so a hung one cannot take the minute's positions with it. The
      document gains `grid`, `constructorOf`, `fastestLap` and `running.{drivers,constructors}`.
      Test: the sweep test in `functions/test/moonshotSettlement.test.js` (grid retried then kept,
      entry list fetched once, laps failure tolerated, numbers checked).
- [x] **Rate budget.** Two feed calls a minute during the race once the grid is known (positions,
      laps), three a minute until the grid is published, up to five on the first minute (sessions,
      grid, drivers), each with a 20 s timeout and at most one 429 retry; the paid tier allows 60
      a minute. ADR-001 notes the change.
- [x] **The app shows it** without touching the provider: `toLiveDoc` parses `running` (negatives
      kept, non-numbers dropped, absent on an older document → null); `useMoonshotLive` returns it;
      `src/simple/grid/liveScore.ts` gives each tile its number (Ace doubled only when the pick may
      be Ace, the same cap the server applies) and the roster its sum, so the tiles and the stat
      row cannot disagree. The listener now runs whatever the Moonshot availability (the Moonshot
      card keeps its own availability check).
- [x] **Tile and stat row.** While the race is in its window and the document carries a running
      score, each filled tile's trend corner shows `LIVE +N` (negative in the negative colour)
      with a slowly pulsing dot; the LAST RACE stat reads `LIVE · SO FAR` with the roster total.
      Before the sweep's first write, and outside the window, the screen is exactly as before.
      Accessibility labels say "live … this race so far, running score".
- [x] **Gated as F-111 is.** Nothing happens unless `config/app.moonshot.liveTiming` is true; the
      sweep does not even pull. `DESIRED.liveTiming` in `setMoonshotConfig.js` stays **false**;
      the switch is still conditioned on the provider's written confirmation (ADR-001), which
      should now name the running score as part of the in-app surface.
- [x] Tests: `node --test functions/test/*.test.js` passes; root jest passes
      (`__tests__/simple/liveScore.test.ts`, `moonshot.test.ts` extended); `tsc --noEmit` clean;
      web screenshots of the live tiles and stat row at `docs/design/grid/verify/F-129-*.png`.

## Targets

(The app half ships with the next store build; the server half with a `functions-deploy` op naming
`moonshotLiveSweep`. Until the switch is on, both are inert.)

## Data
No user data. The document is per race, readable by any signed-in user like the positions already there, written by
the server from the provider's feed under the ADR-001 arrangement. No request or response body is
logged.

## Performance budget
Server: one extra feed call a minute (laps, a few hundred KB late in a race) and three once per
race; one Firestore write a minute as before, a few KB larger. App: one listener as before; the
tile re-renders once a minute while live; the pulse is a native-driver opacity loop on a 6 px dot.

## Deploy
1. Merge; `functions-deploy` op with `only=moonshotLiveSweep` (any time; inert while the switch is off).
2. Next store build carries the app half.
3. Live-timing switch: unchanged from F-111/F-128 — only after the provider's written confirmation
   that covers positions and the running score in the free app; then the `uc-script` op on
   `setMoonshotConfig.js` with `DESIRED.liveTiming` set true in the same change.

## Out of scope
- Retirement detection (no flag in the positions feed; the laps data could infer it, but a wrong
  guess would show a penalty that the classification then reverses).
- League-wide live standings (the round report and standings settle from the official result).
- Pit Wall's live view (its own code base and arrangement).
- Streaming (MQTT/WebSocket): one document a minute is the budget ADR-001 describes.
