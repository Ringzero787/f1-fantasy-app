# F-095 — UC: the ace lock holds on the server, not only in the app

Created: 2026-10-03 · Status: planned · **Not fixed. This is the write-up of a live gap.**

## The gap
Undercut (root app, plus the Pit Wall portal and the Firestore rules).

The ace doubles a driver's points. It locks at **race start** — later than the roster, which locks
at qualifying — and that later lock exists **only in the client**:

| | locks when | enforced by |
|---|---|---|
| roster (drivers, constructor, budget) | qualifying | `isLocked` on the team doc, the rules' protected-field list, and the team callables |
| **ace** | **race start** | **`lockout.ts:102` in the app, and nothing else** |

- `firestore.rules` lets an owner update any field except a named list. **`aceDriverId` is not on that
  list**, and `isLocked` is protected *from being changed* rather than consulted as a condition.
- `web/pitwall/src/lib/teamApi.ts:62` writes `aceDriverId` with a direct `updateDoc`; the app writes
  it through `syncTeamToFirebase` after an equally client-side check in `team.service.ts:347`.
- `functions/src/scoring/calculatePoints.ts:318` reads `team.aceDriverId` **live** when it scores,
  and re-checks only `ACE_MAX_PRICE`. It never asks whether the race had started.
- `raceSnapshots` is built *during* scoring (`calculatePoints.ts:382`). It records what was scored.
  It does not freeze anything beforehand, so it is not available as the authority.

**So: between lights out and the moment scoring runs, a player can set their ace to whoever is
winning and have those points doubled.** That window is hours wide. It needs no exploit beyond the
Firebase web SDK and the user's own credentials.

## What is NOT the gap, and why the obvious fix is wrong
A one-line rule denying `aceDriverId` changes while `isLocked == true` was written and reverted
before it reached production. It would have broken a designed feature: `isLocked` is the
*qualifying* lock, and moving the ace after seeing qualifying — right up to lights out — is
deliberate. `lockout.ts:101-102` says so in two lines:

```
isNaturallyLocked    = now >= lockTime        (qualifying)
isAceNaturallyLocked = now >= raceStartTime   (race start)
```

Any fix has to distinguish the two locks. The rules cannot read a race start time without a `get()`
against the race document, which the team doc does not currently name.

## Shape of the fix (not built)
The cheapest honest version is a second pass in the lock sweep that already exists.

1. `functions/src/locks/teamLocks.ts` runs every 15 minutes and stamps `isLocked: true` at
   qualifying. Add a pass that stamps a separate field — `aceLocked: true`, say — once
   `schedule.race` has passed, and clears it with the existing unlock.
2. `firestore.rules`: deny `aceDriverId` diffs when that field is true, guarded with `in` so a
   document written before the field existed is not made unwritable (reading a missing field is an
   error, and an error denies).
3. The app and the portal read the field instead of computing the lock from race times, so the three
   agree rather than coinciding.

A sturdier alternative is to freeze the ace at race start into the snapshot and score from it, which
also fixes any future field that wants a race-start lock. It is a larger change to the scoring path
and wants its own review.

## Why it is written down rather than fixed
Found by the security gate on PR #151 while reviewing an unrelated Pit Wall change, and confirmed by
reading the rules, the writer and the scorer. It is pre-existing, it is not caused or widened by any
change in flight, and the first fix attempted for it was wrong in a way that would have broken a
real feature on a Saturday night. It deserves a change of its own, with a test that proves the
qualifying-to-race-start window still works.

## Evidence
- `firestore.rules` — `fantasyTeams` update rule, protected-field list without `aceDriverId`
- `web/pitwall/src/lib/teamApi.ts:62` — direct `updateDoc({ aceDriverId })`
- `src/services/team.service.ts:347` — `if (!team.lockStatus.canModify) throw` (client-side)
- `src/utils/lockout.ts:101-102` — the two different lock times
- `functions/src/scoring/calculatePoints.ts:318-325` — live read, cap re-checked, lock not
- `functions/src/scoring/raceSnapshots.ts:120` — ace recorded, but at scoring time
- `functions/src/locks/teamLocks.ts:126` — where a race-start pass would go

## Severity
A player can inflate their own score in a league others are playing honestly, and the Pit Wall Pass
makes it a paid product sitting next to an unfair ladder. No data is exposed and no other account is
reachable; the harm is competitive integrity.
