# F-117 — UC: the Firestore rules tests run in CI

Created: 2026-10-09 · Status: building · Design source: a gap recorded as open in F-104's notes
since 2026-10-06 — "`npm run test:rules` is not in the AIDLC CI test command"

## Goal
Undercut (repo-wide). `rules-tests/` holds 72 tests that are the **enforcement** half of five
features — F-056, F-095, F-098, F-104 and F-105 — and the blocking test command never ran them, so
every one of those security properties was verified on exactly one developer machine. It could not
have run in CI even if the command had named it: the runner starts the cached Firestore emulator
jar directly, and a GitHub runner has no cached jar and no firebase CLI, so it would have taken a
fallback that needs a JDK the runner does not default to. This makes the suite self-provisioning
and puts it in the gate that blocks a merge.

## Acceptance criteria
- [x] **`npm run test:rules` is in the blocking test command** (`.aidlc/aidlc.yaml`), so a rules
      regression fails a PR instead of waiting for someone to remember. Placed immediately after
      the compiled-functions tests — step 4 of 9 rather than last — so a cheap rules failure does
      not wait behind the pitwall `npm ci` and vite build, and so it reuses the functions build it
      needs rather than repeating it at the end of the chain.
- [x] **The runner provisions its own emulator.** With no cached jar it downloads one, so it works
      on a bare runner. A cached jar is still preferred, so the build box keeps using whatever the
      firebase CLI already put there, and the JDK-21-only `firebase emulators:exec` path survives
      only for a machine with no `java` at all. Verified by running from an empty cache directory:
      it fetched the jar and all 72 tests passed.
- [x] **The jar that is about to be executed is hashed — cached or downloaded.** It is fetched over
      the network and then executed, so an unpinned fetch is a supply-chain hole rather than a
      convenience. The first version pinned only the download path and otherwise ran whatever
      `ls … | sort -V | tail -1` returned; the security read planted a
      `cloud-firestore-emulator-v9.9.9.jar`, and a symlink named that, and showed both sorted above
      the pinned jar and executed with the pin never consulted — JVM code execution for anyone who
      could write one file into the cache. The jar is now selected by its **pinned filename**,
      a symlink at that path is refused, the digest is checked before execution, and verification
      happens **after** the move so the bytes executed are the bytes checked. Verified by running
      all four cases: symlink → refused; corrupt file → refused with both digests; planted
      `v9.9.9` → ignored, pinned jar fetched, 72 pass; warm cache → 72 pass.
- [x] **The emulator runs with a scrubbed environment.** In CI the suite runs inside the gate step,
      which exports `GH_TOKEN` with `pull-requests: write` plus the trademark API secrets. A jar
      fetched over the network has no business seeing them. The pin is what makes it trustworthy;
      this is the second layer.
- [x] **The download cannot be downgraded or stall the job**: `--proto '=https'
      --proto-redir '=https'` (curl allows an https→http redirect by default) and `--max-time 300`.
      The temp file is `mktemp`, not a predictable `$$` name that could be pre-created as a symlink
      for `curl -o` to follow into an arbitrary-file overwrite.
- [x] **A drift test guards the wiring, not the rules** (`scripts/rulesTestsInCi.test.js`): the
      blocking command still names the suite, `test:rules` still points at the runner, the suite is
      not empty, the jar is selected by its pinned name, and the symlink and digest refusals are
      still inside `verify_jar`. Commented-out lines do not satisfy any of it, and it reads the
      config as raw text rather than importing `js-yaml`, which is only transitively present.
      **Every assertion was checked by breaking the property it guards**: removing the symlink
      refusal, restoring the `sort -V` selection, making `verify_jar` always succeed, and dropping
      `test:rules` from the command each fail it. The hash-mismatch case is **behavioural** — it
      runs the script against a planted bad jar — because the first version of that assertion was
      text-matching whose slice spanned the whole file, so an unrelated `rm -f` satisfied it and the
      property could have regressed with the test still green.
- [ ] **CI actually runs it green.** This is the one thing that cannot be proven from here: whether
      a GitHub runner has `java` on PATH. If it does not, the fallback needs the firebase CLI and
      the right JDK, and the honest fix is then a workflow change — which has to go through
      `aidlc sync`, since `.github/workflows/aidlc-pr.yml` is rendered and must not be hand-edited.

## Targets
- web/repo: CI configuration and a shell runner. No app, server or rules behaviour changes.

## Data
No user data, no collections, no production access. The emulator runs against a throwaway
`demo-uc-rules` project on a kernel-chosen free port and is killed on exit.

## Out of scope
- The rules themselves. This changes only whether their tests run.
- `syft`/`cosign` for G13's provenance evidence — a different gap, see
  `.aidlc/releases/undercut-v2.5.1.provenance.md`.
