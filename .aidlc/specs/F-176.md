# F-176 — UC: Save a lineup in one call

Undercut (repo root). Status: building.

## Goal
Saving a lineup should feel immediate: one server round trip whatever the number of moves, all or nothing, with exactly the rules the single moves enforce.

## Acceptance criteria
- [ ] **After deploy, a Save is one call, measured from production logs** (`gcloud functions logs read applyLineupSecure`):
  - a three-move save makes 1 call instead of 3;
  - execution is at most 1.5 s on a warm instance;
  - first call to finish is at most 5 s on a cold start, about one cold start instead of three.
- [x] **Every rule is the same as the single moves'**, because the single moves now run the same steps: `addDriverSecure`, `removeDriverSecure`, `setConstructorSecure` and `removeConstructorSecure` call `lineupSteps.ts` and hold no rules of their own (a test fails if one gains its own copy again).
- [x] **All or nothing:** a refusal at any step writes nothing (emulator test).
- [x] **Outcome shown to the player:**
  - a refusal says "Lineup not saved";
  - a timeout or dropped connection says "Save not confirmed" and re-reads the roster from the server;
  - only the single-move fallback can still say "Lineup partly saved".

## Why
The owner reported, on 2026-11-25, that saving a lineup (sell a few drivers, buy one) "took a solid 5-7 seconds".

**Cause, from code and production logs.** Save sent one roster callable per move, each awaited before the next (`GridPickerScreen.applyPlan`):
1. `removeDriverSecure` for each driver sold;
2. `removeConstructorSecure` or `setConstructorSecure`;
3. `addDriverSecure` for each driver bought.

**Why each call was slow.** The four are first-generation functions at 256 MB that ran about 30 times in 30 days, so nearly every call started cold.
- On 2026-11-25 at 00:38 UTC, a three-move save measured 1.0 to 1.4 s of execution per call, plus 2.6 to 3.3 s of cold start between calls: about 10 s end to end.
- On a warm instance a call takes 0.4 to 0.6 s.

**Load is not the problem.** More users do not make it worse: each save writes only that user's team, and steady traffic keeps instances warm.

## What
- [x] **The callable.** `applyLineupSecure({ teamId, sellDrivers, sellConstructor, buyConstructor, buyDrivers })` applies the whole change in one call and one transaction.
  - It reads every price the plan needs in parallel.
  - All or nothing: a refusal at any step writes nothing, so the "Lineup partly saved" state cannot happen through it.
  - It runs at 512 MB, because a first-generation function's CPU, and so its cold start, scales with memory.
- [x] **One copy of the rules.** They live as pure steps in `functions/src/teams/lineupSteps.ts`, which the four single-move callables now call too: the same sale quote (3% a race left, waived in the grace period and for reserve picks), the banking from `totalPoints` into `lockedPoints`, ace clearing, lockouts, the F-169 contract caps and six-in-a-row run, and the budget check. They run in the order the app sent the single moves: driver sales, constructor sale or swap, driver buys.
- [x] **The write.** One `set` with `mergeFields`. Each listed field is replaced, so `driverStreaks` drops stale keys as `removeDriverSecure`'s `update()` does. The top-level `constructor` key is written as data, which `update()` cannot do.
- [x] **The app.** `GridPickerScreen` saves through `teamStore.applyLineup` and adopts the team the server returns. It falls back to the single moves in demo mode, and when the callable answers NOT_FOUND (a build that reaches players before the function is deployed).
- [x] **Faster single moves.** The add-driver, remove-driver and set-constructor callables now read the season clock and the lock state in parallel. Released builds still use them.
- [x] **Tests.**
  - `functions/test/lineupSteps.test.js`: every rule and refusal.
  - `rules-tests/applyLineup.integration.test.js`: the real transaction and write against the emulator, covering the `constructor` key, the replaced streaks, the points banked, all or nothing, and the owner and lock checks.
  - `__tests__/utils/callableErrors.test.ts`.

## Not in this change
- **`minInstances: 1`** on `applyLineupSecure` would remove the remaining single cold start. It costs money (about $10 a month for one always-on 512 MB first-generation instance; check the current price), so it is the owner's decision and its own op, for example on race weekends only.
- **Moving the roster functions to second generation** (concurrency, CPU boost at startup), and making the heavy imports lazy (Gemini, nodemailer, rss, storage) so roster functions load less code.
- **Closing the sheet before the server answers.** The save is now one call, so this is simple to do later.

## Platforms
- Every build that carries this change: Play, App Store, Amazon, and web.
- The server function must be deployed for the speed-up. The fallback keeps builds without it working.

## Data
- No new fields. Each save writes these `fantasyTeams/{id}` fields: `drivers`, `constructor`, `budget`, `totalSpent`, `lockedPoints` and `totalPoints` (as increments), `driverStreaks` (replaced when a driver is sold), `aceDriverId` and `aceConstructorId` (cleared when the ace is sold), `racesSinceTransfer` and `updatedAt`.
- The best-effort `transactions` log gets one row per sale and per buy.

## Decisions (one copy of the rules, where the old copies differed)
- **Negative points on a constructor swap.** A swap now banks the outgoing constructor's points when they are negative too, as a plain constructor sale always did. `setConstructorSecure` used to skip a negative total on a swap and leave it counting.
- **A missing budget.** A team with no `budget` field starts a sale from the default budget, as buys always did. The sale callables used to start it from 0. Every team gets a budget when it is created, so this is an edge case only.
- **Constructor swap log.** A swap now writes a `sell` row as well as the `buy` row.

## Deploy
- Functions through `aidlc op`: `applyLineupSecure`, plus `addDriverSecure`, `removeDriverSecure` and `setConstructorSecure` for the parallel reads.
- Then the app build. The order is safe either way, thanks to the fallback.
