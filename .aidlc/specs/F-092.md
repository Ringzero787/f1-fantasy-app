# F-092 — UC: a purchase grants once, not once per launch

Created: 2026-10-02 · Status: building

## Goal
Undercut (root app). One payment could become one credit on every launch.

`handlePurchaseComplete` granted the three consumable products — a league expansion, an extra league
slot, a pack of avatar credits — from the device the moment the store handed a purchase over:
`pendingExpansionCredits + 1`, `leagueSlotCredits + 1`, `+ AVATAR_PACK_CREDITS`, straight into
persisted state, *before* any server round trip. It then finished the transaction and only
afterwards recorded it with `validatePurchase`, with the failure swallowed and the server's
`duplicate` flag thrown away. Nothing remembered which store transactions had already been honoured.

A purchase the store cannot finish is handed back on the next launch — that is the whole point of
`replayHeldPurchases`, added so a failed grant could not strand someone's money — and the replay
goes through the same handler. So if `finishTransaction` could not complete (offline: Play answers
`queryPurchasesAsync` from its local cache but cannot `consumeAsync`), the purchase came back and
granted again. Once per launch, for one payment.

The credits are real: `applyLeagueExpansion` refuses without an unused validated purchase, but
`expansionFallback.ts` still returns `fallback` while `INTERIM_UNVERIFIED_EXPANSION_FALLBACK` is on,
and `firestore.rules` permits the client's own `maxMembers` raise. The Pit Wall Pass was never
exposed: the server owns that grant and keys it on the purchase record.

Found by the G05 model review while reading the F-091 branch, in code shipped as versionCode 65.

## Acceptance criteria
- [x] One store transaction grants at most once on a device, however many times the store hands it
      back.
- [x] Two independent guards, because neither covers the other's case:
      - the server's `duplicate` flag, which is the only thing that knows about a purchase made on
        another device or before a reinstall, and
      - a **persisted** list of transactions this device has honoured, which is what makes the
        replay loop safe when the server cannot be reached at all.
- [x] The local key is `platform:storeTransactionId`, the same primitive and the same shape the
      server keys its `purchases` document on — Apple's transaction id, Google's and Amazon's
      purchase token — so both ends agree on what "the same purchase" means without asking.
      `amazon:X` and `android:X` are different keys.
- [x] The server is asked **before** anything is granted, and the transaction is finished **after**
      the grant is recorded. A finished transaction is one the store will not hand back, so
      finishing before recording is how a purchase gets lost.
- [x] `recordPurchaseOnServer` throws on failure for every product, not just the pass. A purchase
      that cannot be validated is left with the store and retried on the next launch — which is what
      the pass has always done — rather than granted on trust.
- [x] A live purchase that carries no stable identifier is still granted (someone has just paid and
      the server says it is new). A **replay** with no identifier is not: it cannot be told apart
      from one already honoured, and the server sync is the way back.
- [x] A replayed purchase grants silently. The alerts ("League expansion unlocked!") belong to
      someone standing at the till, not to a launch.
- [x] The avatar pack credits the signed-in account when the pending context is gone. On a replay
      the `pendingUserId` set by the buy call is a launch in the past, so the old code granted
      nothing *and finished the transaction anyway* — paid for, never delivered. If there is no
      account to credit, the transaction is left unfinished rather than consumed for nothing.
- [x] The decision is a pure function (`src/store/purchaseGrant.ts`) and unit-tested, including the
      offline replay loop, the reinstall case, and the no-identifier case.
- [x] The **ordering** is held by a static test (`__tests__/store/iapWiring.test.ts`). A refactor
      that moves the grant back above the server call, or the finish above the honoured-list write,
      reintroduces the bug exactly, and no behavioural test would notice: reproducing it needs a
      real store, a real payment and a failed consume.

## Targets
- android
- ios
- amazon

## Data
No new data leaves the device and no new field is collected. One new persisted local value:
`honouredTransactions`, a capped list (100) of `platform:storeTransactionId` strings in the same
secure store the rest of the purchase state already uses. These are store transaction identifiers
for the device's own purchases — the same values already sent to `validatePurchase` and already
stored server-side in `purchases.storeTransactionId`. Nothing about another person, and nothing new
transmitted anywhere.

## Performance budget
No new dependency, no new call. It *removes* a call in the already-honoured case: a replay this
device has granted for does not ask the server at all, which is also what lets an offline replay
finish the transaction instead of looping forever.

## Out of scope
- `INTERIM_UNVERIFIED_EXPANSION_FALLBACK`, the server-side flag that lets an expansion through
  without a validated purchase. It is the other half of why a spurious credit converted into real
  slots, and turning it off is a separate decision with its own blast radius.
- The client's permission to raise `maxMembers` directly in `firestore.rules`.
- Making the three consumables server-authoritative the way the pass is. That is the right end
  state and a much larger change; this makes the current design honest.

## Known gaps
- **A reinstall still relies on the server.** The honoured list is per-device and is wiped, so a
  purchase the store still holds after a reinstall is deduplicated by the server's `duplicate` flag
  alone — correct, but it means the offline-plus-reinstall combination grants nothing until the
  server can be reached. That is the safe direction to fail.
- **The cap is a cap.** Past 100 honoured transactions the oldest key is forgotten. A store that
  hands back a transaction older than a player's last hundred purchases would grant it again; at one
  or two purchases a season this is not reachable, and the server flag still covers it.
- **No test exercises the real handler** — only the pure decision and the static ordering. There is
  no component or store test harness for a zustand store wrapping `expo-iap` in this codebase.
