# F-077 — UC: Pit Wall in the app — portal handoff, pass status and pass-only pick marks

Created: 2026-09-24 · Status: building (iOS and Android sell in-app from 2.4.0; amazon still links out)

## Goal
Undercut (root app). Pit Wall is live on the web, and the app has no way to reach it: the portal's own sign-in screen already tells people to open it from their Profile, which is a promise the app does not keep. Someone who signs in with Amazon cannot reach it at all, because Amazon sign-in cannot run in a browser popup. This feature gives the app a way in, shows whether the account holds a pass, and makes the pass worth something inside the app by marking the pick the projection model would take at the moment a driver is being chosen.

## Acceptance criteria
- [ ] A `PIT WALL` row sits under `LEAGUE` in the Profile screen. It calls `pw-createPortalHandoff`, opens `https://<portal>/h#<code>&src=profile` in the system browser, and the portal signs in as the same account without a password. If the handoff fails for any reason the row still opens the portal, where normal sign-in works.
- [ ] The row shows the pass state: the expiry date for a holder, the configured free label otherwise. Closing the browser forces an ID-token refresh, so a pass bought on the web during that visit shows without restarting the app.
- [ ] Whether the row appears at all, its copy, the portal address and the per-platform mode come from the `pitwall` block of `config/app` (ARCHITECTURE section 8). A missing, disabled or malformed block renders nothing. A beta list of uids or league ids, while non-empty, limits the surface to those users. A `minAppVersion` above the running build hides it. Versions compare numerically, so 2.10.0 is above 2.9.0.
- [ ] The handoff code is a credential, so the destination is restricted to a fixed allowlist of portal hosts, not any `https` address the config names.
- [x] ~~**No purchase wording anywhere in the app**, on any platform.~~ **Superseded 2026-10-01.** F-060 brought the purchase library back in 2.4.0, and `pitwall.pass.season` was submitted to Apple with build 45. Leaving iOS on `open` while that product is in review gives the reviewer a web page instead of a purchase, which fails as both an unlocatable purchase and a guideline 3.1.1 link-out, so iOS now sells in-app. **Android followed 2026-10-01** once its Play product was Active, the Cloud Functions runtime account held both Play order permissions, and versionCode 63 carrying the purchase lifecycle was live on production. Amazon keeps this criterion until its product is active.
- [x] Selling adds a row rather than changing the existing one. A single row that flips to "Get the pass" takes the only route to the portal away from everyone who has not paid, including the free tier. A platform in `iap` shows the portal row and a pass row.
- [x] The price shown is the one the storefront formatted, never the catalogue's `$14.99`, which is the US price and the wrong currency everywhere else. With no price from the store the row says "Get the pass" rather than a figure.
- [x] The purchase lifecycle is started at the app root. `initializeIAP` had no call site in any released version, so the connection was never opened and the completion listener never registered: a buyer could be charged and granted nothing, and an unfinished transaction redelivered at launch had nobody listening. A static test now fails if the call site goes again.
- [ ] Pass holders see this round's projection on every row of the picker, read from `pw_pages`; a `PIT WALL PICK` mark on the row the model would take; a `BEST VALUE` mark on the best points per $100 when that is a different row; and `PROJ` as a third sort beside `PTS` and `$`.
- [ ] A mark can never suggest a move the picker would refuse: the recommendation ranks only rows the picker has already left selectable, so the budget, the squad size, driver lockouts and the weekend lock all still apply.
- [ ] Without an active pass nothing above appears, and the app does not attempt the read: the Firestore rules on `pw_pages` are the real gate and would refuse it. Signing out clears the cached pass and projections.
- [ ] The rules, the config gating, the projection coercion and the recommendation are pure modules, unit-tested without a React Native runtime; every Firebase call lives in one module.

## Targets
- android
- ios
- amazon

## Data
Reads the signed-in user's `pw` custom claim (pass expiry) and, for pass holders, the published `pw_pages` document. Sends the user id to `pw-createPortalHandoff` to mint a sign-in code, and the uid and league id are matched against the server-side beta list in memory. Nothing new is stored on the device: the pass and projections are held in memory only, because a stale copy restored from disk would mark the wrong picks.

## Performance budget
No new dependency, so no change to bundle size or cold start. Two extra reads for a pass holder on app start (one token refresh, one document); none for anyone else.

## Out of scope
- Buying the pass in the app on Amazon, until its store product is active (the config mode gates each platform separately).
- Distinguishing Android builds that carry the purchase lifecycle from ones that do not. versionCode 62 and 63 are both version 2.4.0, and the version gate compares versions rather than version codes, so 62 sees the purchase row and is refused by Play at the billing call. Accepted deliberately: 63 had rolled out, and the failure is a refusal rather than a charge. A future change that needs this distinction has to raise the app version, not the version code.
- The upgrade sheet, the team-screen teaser and the weekend-recap teaser (ARCHITECTURE section 8 surfaces 2 to 4).
- Rendering portal pages inside the app.
