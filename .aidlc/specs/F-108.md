# F-108 — UC: Moonshot in the app

Created: 2026-10-06 · Status: implemented · Design source: `docs/design/moonshot/SPEC.md` §2, §5, §8, §11–§13, §16, §17, §20, §21, §32, §34

## Goal
Undercut (root app). The whole player experience: a locked teaser before midseason, a Moonshot tab on the driver tile sheet, the quote → confirm flow in the game's own words, the declaration in the league feed, the live card on race day, and the one-time coach marks. Understandable in seconds: Driver · Prediction · Chance · Risk · Reward.

## Delivery
Two PRs. **PR 1 (this build):** config gating, the tile-sheet row (teaser before unlock), the flow sheet, the Team-screen card with Cancel before lock, the standings and race-leaderboard column, the copy table with its terminology test, and a `moonshotMenu` callable (F-106 shape) so the sheet opens with one round-trip. In PR 1 the row is reached from roster tiles only, so every PR-1 Moonshot is a Double Down; the design's primary case (any driver on the entry list, from the picker) and EXACT FINISH (when enabled) are PR 2's. **PR 2 (this build):** picker entry for non-roster drivers (a 🚀 on every driver row of the picker while a call is open), EXACT FINISH when `predictionTypesEnabled` has it (a position grid; the quote prices the position), the league feed on the LEAGUE tab (this race's locked declarations through a new `moonshotLeagueBoard` callable — decided on the server clock so no client list query on `moonshots` is needed — plus the season's `activity` history), the race-day live card (positions from the OpenF1 feed — which only the admin screens used before — polled each minute while the race window is open **and only when `config/app.moonshot.liveTiming` is on**: ADR-001's data arrangement covers the Pit Wall ingest, not every player's device, so the owner switches this on deliberately; off, the card shows PENDING and settles from the official result. IN / OUT / ONE POSITION AWAY / PENDING, then the settled line; league-mates' locked calls beneath; the window closes three hours after the start, six if the server still says in progress), coach marks (four cards, once per account via `users/{uid}.moonshotTutorialSeen`, re-opened from the sheet's ⓘ), analytics (a thin `track()` — Firebase Analytics on the web build, no-op on native until the native module is adopted; every SPEC §32 client event is fired), demo-mode fixtures so screenshots and web verification can walk the flow without a model or config. The deeper model view (circuit performance, form, qualifying projection, confidence) needs data only the Pit Wall holds → F-109.

## Acceptance criteria
- [ ] **Before unlock**: the tile sheet shows a locked Moonshot row with the configured copy ("MOONSHOTS UNLOCK AT MIDSEASON …"). Nothing else renders when `config/app.moonshot.enabled` is false or the round is before `unlockRound`.
- [ ] **Entry**: the tile detail sheet (F-058) gains a 🚀 MOONSHOT row (the sheet has no tab bar; the row sits under the Pit Wall block and opens the Moonshot sheet) for any driver on the roster — a driver not on the roster is reached from the picker in PR 2 — showing tokens left ("YOU HAVE 2 MOONSHOTS") and, if one is already called this race, that call instead of a new one.
- [ ] **Flow** (three screens, no slider): currency (`🏆 CHAMPIONSHIP POINTS · Move up the standings` / `💰 CASH · Build a stronger roster`), prediction (TOP 5 / PODIUM / WIN, each with model chance and reward from the server quote; EXACT FINISH only when enabled), stake (the three configured levels labelled CAUTIOUS / BOLD / ALL-IN), then confirmation showing exactly `HIT +X · MISS −Y` and "This Moonshot locks when race selections lock." Two taps minimum to place; a quote older than its `expiresAt` is re-fetched before confirm. Double Down framing when the driver is on the roster (SPEC §12). Every number on screen comes from the server: the prediction screen's chances and multipliers from `moonshotMenu`, the stake screen's HIT/MISS from `moonshotQuote`.
- [ ] **Before lock**: the call shows on the Team screen with Cancel (cancel returns the token; Change = cancel and call again, since one call per race is the rule and a second confirm would be refused). **After lock**: immutable, and the Change/Cancel controls disappear even if the client clock is wrong (server refusal shown as a sentence).
- [ ] **League feed**: a locked Moonshot appears to league members as the declaration in SPEC §16; hidden before lock — fixed on (the rules and the board callable always hide an open call; `hideBeforeLock` in config is informational, the client does not switch on it), and "locked" means both the call's stamped lock and the race's live lock have passed, so a declaration can never appear while its owner could still cancel.
- [ ] **Race day**: the Race Day screen shows `🚀 YOUR MOONSHOT` with the driver's current position from the live timing feed the screen already uses, and a state chip: IN / OUT / CLOSE ("ONE POSITION AWAY") / PENDING, then HIT / MISSED / VOID after settlement with the SPEC §18 copy. Also shows league-mates' locked Moonshots in a row below.
- [ ] **Coach marks**: a four-step overlay the first time the feature is available (SPEC §20), server-driven copy, shown once per account (`users/{uid}.moonshotTutorialSeen`), re-openable from an info icon on the Moonshot tab. "WHY THIS MULTIPLIER?" opens the model view of SPEC §21 from the published snapshot — predicted finish, expected finish, likely range (what the model carries); form and confidence need data only the Pit Wall holds and are F-109's.
- [ ] **Terminology**: only the words in the SPEC summary; a unit test on the copy table fails on any of the forbidden ones. Watchlist terms appear only in descriptive event names.
- [ ] **Analytics**: every client event in SPEC §32 fired through `src/services/analytics.service.ts` (`track`): opened, currency/prediction/stake selected, quote viewed, confirmed, cancelled, live viewed, model details viewed, tutorial viewed. Delivered to Firebase Analytics on the web build with storage consent **denied by default** (no consent flow exists; nothing is measured until one does and the store/privacy declaration is updated — a privacy read, not this feature's call); a no-op on native builds until the native Analytics module is adopted. The server's structured logs are the record meanwhile. `moonshot_driver_selected` fires from both entry points (tile row, picker). The app has no client analytics path today (no Firebase Analytics, no event service); `moonshot_confirmed`/`moonshot_cancelled` are structured function logs (F-106) and the rest is PR 2's, which decides the path.
- [ ] Verified on Expo web (dark and light) with screenshots in `docs/design/grid/verify/F-108-*.png` — done 2026-10-07 in demo mode (coach marks 1–4, empty team, picker with 🚀 rows, currency, prediction, why-this-multiplier, stake, confirm, called, team card, current call), both themes — and on a device build before release. Not in the demo walk: the live card (needs a race in progress, live timing on), the league feed (needs a league) and EXACT FINISH (off in the demo config, as in V1).

## Targets
- android

## Data
Writes nothing directly: all calls go through the F-106 callables. Reads `moonshots` (own, and league-mates' after lock) and the published snapshot. One per-user flag for the tutorial.

## Performance budget
Tile sheet opens with one extra read (tokens and current call from the team document); quote is one callable round-trip.

## Out of scope
- Pricing, eligibility and settlement (server, F-106/F-107).
- Head-to-head and other prediction types; Final Moonshot.
