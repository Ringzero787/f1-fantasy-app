# F-094 — UC: the sign-in handoff is bound to the device that started it

Created: 2026-10-03 · Status: building

## Goal
Undercut (root app). Close an account-takeover path in the web sign-in handoff built by F-091 and
extended by F-093, before any of the three flows is switched on.

The handoff let the app pick its own `verifier` and sent `state = sha256(verifier)` to the identity
provider. Collecting the filed credential needed only the verifier — so it needed only something the
*claimer* chose:

> Pick a verifier. Build the authorization URL with the matching state (and, for Google, the
> matching PKCE challenge). Send that link to someone. Once they have consented to Undercut before,
> Apple and Google redirect without prompting. Their credential is filed under your state, and you
> claim it.

PKCE does not help: the attacker owns the challenge too. Nothing in the flow distinguished the
device that *started* it from anyone who knew the verifier.

Found by the spec gate on F-093. Latent rather than live — no redirect URI is registered at any
provider yet, so none of the three flows can be driven — which is why this lands before the console
steps rather than after.

## Acceptance criteria
- [x] **Two halves, held by different parties, and it takes both.**
      - The **verifier** is 32 random bytes the app makes before opening the browser; it never
        leaves the device until the claim. `state = sha256(verifier)` is what travels to the
        provider.
      - The **ticket** is 32 random bytes *the server* makes when the credential arrives. It goes
        out only on the redirect, so only the app that received that redirect has it.
- [x] The attack above fails: the ticket reaches the victim's app, and the attacker never sees it.
- [x] The earlier case still fails too: an app that claims the custom scheme and intercepts the
      redirect reads state and ticket, and cannot invert the hash to get the verifier.
- [x] Only the ticket's **hash** is stored. The collection is already closed to clients; a record
      that cannot be replayed by whoever reads it costs one `createHash` call.
- [x] A wrong ticket deletes the record anyway. Someone claiming a credential that is not theirs
      does not get to try again, and the person whose sign-in it was retries from the start.
- [x] All three flows — Apple, Amazon, Google — change together. They share one store, one deep-link
      builder and one redirect reader, so they cannot drift apart.
- [x] **The rate limit counts the right caller.** These run on Cloud Run behind the Hosting rewrite,
      where `req.ip` is a Google frontend address — the same for everybody — so "ten a minute each"
      was really "ten a minute in total", shared across all three providers: eleven requests from
      anywhere would have locked the world out of signing in. The key now comes from the left-most
      `x-forwarded-for` entry. A caller can spoof that; a rate-limit key does not need to be an
      identity, and a spoofable key is strictly better than one everybody shares.
- [x] Google's authorization request sends `prompt=select_account`. Without it a device with a live
      Google session signs in with that account and never shows a chooser — wrong on a shared Fire
      tablet, and the silent path is what a crafted link wants.
- [x] "Link Google" in Profile works on the Amazon build. It still called the native module, which
      cannot run on Fire OS — after F-093 it was the only Google path there that still failed.
- [x] The pure parts are unit-tested with no Firebase or browser runtime: the deep-link builder
      (including that a ticket never rides an error), the redirect reader, and the caller key.

## Targets
- android
- ios
- amazon

## Data
No new personal data and nothing new transmitted. One new field on the existing ten-minute
`auth_handoff` record: `ticketHash`, the SHA-256 of a random value. The ticket itself is never
stored and appears only in one redirect. `firestore.rules` already denies every client access to
that collection.

The rate-limit key changes from a hash of the socket peer to a hash of the forwarded client address.
Both are hashed before they are written (`ipKey`), and no address is logged.

## Performance budget
One `createHash` per file and per claim. No new dependency, no new call, no new document.

## Out of scope
- Making the claim an authenticated call. The caller is mid-sign-in and has no account yet.
- App Check on these endpoints. Worth doing, and a larger change than this one.

## Known gaps
- **The ticket is only as good as the redirect.** On a device where another app wins the custom
  scheme, that app gets the ticket — it just cannot use it without the verifier. The pair is what
  holds; neither half alone was ever meant to.
- **The forwarded address is spoofable**, as above. It bounds a flood from one source rather than
  identifying anyone.
- **Whether `req.ip` is really a frontend address was not proved**, only reasoned. Probing the live
  endpoint showed the limit firing at ten a minute for one caller, which is consistent with both
  readings; settling it needs a second egress address or an instrumented deploy. The change is
  correct either way — with a direct caller the left-most entry is that caller.
