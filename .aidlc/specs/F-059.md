# F-059 — UC: Server-owned league counts, team-name check and scoped team reads

Created: 2026-09-18 · Status: planned

## Goal

Phase two of F-056. Three rules gaps could not be closed there because released builds depend on the loose behaviour: any signed-in user can query any fantasy team (the client checks team-name uniqueness with a global query), `leagues/{id}.memberCount` is maintained by clients, and the owner's client writes `maxMembers` after a purchase. This feature removes each dependency server-side and in the client, so the rules can then be tightened behind the minimum-version gate. It lands in two steps: **step A** (this change: functions + client, safe to deploy and ship at any time) and **step B** (rules, a separate gated change that must not deploy until `config/app.minVersion` is at or above the first client release containing step A).

## Acceptance criteria — step A
- [ ] Callable `checkTeamNameAvailable({ name, excludeTeamId? })` trims and bounds the name (2–30), honours `excludeTeamId` only for a team the caller owns, and answers with the Admin SDK; `teamService.createTeam` and `updateTeamName` use it and run no `fantasyTeams` name query (jest: `__tests__/services/teamNameCheck.test.ts`).
- [ ] Triggers `onLeagueMemberWritten` (member create / delete / pending↔approved) and `onLeagueMemberCountChanged` (anyone changes `memberCount`) call `reconcileMemberCount`, which recounts approved members in a transaction and writes only when the stored count is wrong, so released clients' own ±1 writes are corrected and the two triggers cannot loop (emulator: `rules-tests/memberCount.integration.test.js`). Both triggers retry (reconcile is idempotent) and `reconcileAllLeagueMemberCounts` sweeps every league daily, bounding any missed event. The live join rule allows one slot of slack on the count so a released client racing the recount at the last free slot does not error.
- [ ] The client no longer writes `memberCount` in `joinLeague`, `leaveLeague`, `removeMember` or `approveMember`.
- [ ] Callable `applyLeagueExpansion({ leagueId })` spends exactly one store-verified, unused `league.expansion` purchase belonging to the caller, in a transaction, and adds `SLOTS_PER_EXPANSION` to a league the caller owns; `leagueId` must be a plain document id. The League Manager calls it first; when the call does not confirm it re-reads the league and follows `expansionNext()` (pure, jest-covered): capacity already grew → done (the reply was lost, not the write); the server refused the request itself (`permission-denied`, `not-found`, `invalid-argument`, `unauthenticated`) or an unknown code → fail, no write; a transport failure, or `failed-precondition` (no verified purchase on record) while `INTERIM_UNVERIFIED_EXPANSION_FALLBACK` is true → the existing direct write, so a customer whose store purchase completed is never left without slots while validation is unproven. The fallback grants nothing the owner rule does not already allow and is removed in step B.
- [ ] `validatePurchase` verifies Google Play tokens against `com.undercut.app` (it used `com.f1fantasy.app`, so Android validation could never succeed; production has zero purchase records); a node test pins it to `app.config.js`'s `android.package`.
- [ ] Trigger wiring (document paths, event types, `retry`, the schedule, the exports) is asserted from the compiled `lib/index.js`; the Functions emulator is not available on the build box (JDK 17), so the triggers themselves are first exercised on deploy.
- [ ] Pure helpers (`approvedMemberCount`, `membershipChanged`, `normalizeTeamName`, `isTakenBy`, `isUnusedExpansion`) are covered by `node --test functions/test/leagueCountAndTeamName.test.js`.
- [ ] `npx tsc --noEmit`, `npx jest --ci`, the functions build + tests and `npm run test:rules` pass. Deploy order: `aidlc op rules-deploy` (the slack) then `aidlc op functions-deploy`.

## Acceptance criteria — step B (gated; separate change)
- [ ] Only after `config/app.minVersion` ≥ the first client release with step A: `fantasyTeams` `allow list` becomes own teams, teams in a league the caller belongs to, or admin; `leagues/{id}` accepts updates from the owner only. Both verified in `rules-tests/` and deployed through `aidlc op rules-deploy`.
- [ ] Only after a real store purchase has been validated end to end (a license-tester purchase on a device): the owner branch stops accepting `maxMembers` changes and the client fallback is removed.

## Targets
- firebase (functions; rules in step B)
- android
- ios

## Data
No new user data. `purchases` documents gain `appliedToLeagueId` / `appliedAt` when spent.

## Performance budget
One callable round-trip on team create / rename (replaces one query). One trigger invocation per join / leave / approval and per `memberCount` write, each reading the league's members (leagues are capped in the low tens).

## Out of scope
- True uniqueness of team names: the check and the team write are separate steps, so two simultaneous creates can still collide, exactly as with the old client query. Closing that needs a names-reservation document written in the same transaction as the team.
- Restricting who can read league documents and invite codes (needs a join-by-code callable; separate decision).
- Amazon Appstore receipt validation (the Amazon build has no server-verifiable purchase path today).
