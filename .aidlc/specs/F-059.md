# F-059 — UC: Server-owned league counts, team-name check and scoped team reads

Created: 2026-09-18 · Status: planned

## Goal

Phase two of F-056. Three rules gaps could not be closed there because released builds depend on the loose behaviour: any signed-in user can query any fantasy team (the client checks team-name uniqueness with a global query), `leagues/{id}.memberCount` is maintained by clients, and the owner's client writes `maxMembers` after a purchase. This feature removes each dependency server-side and in the client, so the rules can then be tightened behind the minimum-version gate. It lands in two steps: **step A** (this change: functions + client, safe to deploy and ship at any time) and **step B** (rules, a separate gated change that must not deploy until `config/app.minVersion` is at or above the first client release containing step A).

## Acceptance criteria — step A
- [ ] Callable `checkTeamNameAvailable({ name, excludeTeamId? })` trims and bounds the name (2–30) and answers with the Admin SDK; `teamService.createTeam` and `updateTeamName` use it and run no `fantasyTeams` name query (jest: `__tests__/services/teamNameCheck.test.ts`).
- [ ] Triggers `onLeagueMemberWritten` (member create / delete / pending↔approved) and `onLeagueMemberCountChanged` (anyone changes `memberCount`) call `reconcileMemberCount`, which recounts approved members in a transaction and writes only when the stored count is wrong, so released clients' own ±1 writes are corrected and the two triggers cannot loop (emulator: `rules-tests/memberCount.integration.test.js`).
- [ ] The client no longer writes `memberCount` in `joinLeague`, `leaveLeague`, `removeMember` or `approveMember`.
- [ ] Callable `applyLeagueExpansion({ leagueId })` spends exactly one store-verified, unused `league.expansion` purchase belonging to the caller, in a transaction, and adds `SLOTS_PER_EXPANSION` to a league the caller owns; the League Manager calls it first and falls back to the existing direct write if it is unavailable, so a paying customer is never left without slots.
- [ ] `validatePurchase` verifies Google Play tokens against `com.undercut.app` (it used `com.f1fantasy.app`, so Android validation could never succeed; production has zero purchase records).
- [ ] Pure helpers (`approvedMemberCount`, `membershipChanged`, `normalizeTeamName`, `isTakenBy`, `isUnusedExpansion`) are covered by `node --test functions/test/leagueCountAndTeamName.test.js`.
- [ ] `npx tsc --noEmit`, `npx jest --ci`, the functions build + tests and `npm run test:rules` pass. Functions deploy through `aidlc op functions-deploy`.

## Acceptance criteria — step B (gated; separate change)
- [ ] Only after `config/app.minVersion` ≥ the first client release with step A: `fantasyTeams` `allow list` becomes own teams, teams in a league the caller belongs to, or admin; `leagues/{id}` accepts updates from the owner only. Both verified in `rules-tests/` and deployed through `aidlc op rules-deploy`.
- [ ] Only after a real store purchase has been validated end to end (a license-tester purchase on a device): the owner branch stops accepting `maxMembers` changes and the client fallback is removed.

## Targets
- firebase (functions; rules in step B)
- android
- ios

## Data
No new user data. `purchases` documents gain `appliedToLeagueId` / `appliedAt` when spent.

## Performance budget
One callable round-trip on team create / rename (replaces one query). One trigger invocation per join / leave / approval and per `memberCount` write, each reading the league's members (leagues are capped in the low tens).

## Out of scope
- Restricting who can read league documents and invite codes (needs a join-by-code callable; separate decision).
- Amazon Appstore receipt validation (the Amazon build has no server-verifiable purchase path today).
