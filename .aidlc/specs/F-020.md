# F-020 — UC: Lock teams created inside the quali window

Created: 2026-09-11 · Spec filled 2026-10-14 · Status: planned · ROADMAP Now (S).
F-118 (2026-10-09) closed the *post-sweep* half: once `autoLockTeams` has flipped the race to
`in_progress` and published `config/lockState`, `createTeamSecure` locks a mid-weekend team and
the roster callables / ace rules refuse an unswept one. This feature is the half that is still
open: a team created **inside the lock window before that sweep has run**, and a team the
shipped client still creates with a bare `addDoc` (`isLocked: false`) so the UI and scoring
treat it as unlocked even when the callables already refuse.

## Goal
Undercut (app + server). `autoLockTeams` runs every 15 minutes and only looks at `upcoming`
races. A team created after lock time is due, before the next sweep (or via `addDoc` after the
sweep), is stored unlocked. The player can still pick a roster with qualifying already running,
and scoring keys Phase 3.5 / lock-sensitive reads on `isLocked`. Lock that team at creation
when the calendar says the window is open, send the app through `createTeamSecure`, and have
the sweep catch any unlocked team while the weekend is live.

## Acceptance criteria
- [x] **One predicate.** `isRaceDueForLock(race, nowMs)` in `functions/src/utils/lockTime.ts`
      is the same rule `autoLockTeams` uses to pick a due race: usable lock time, usable race
      start, weekend not more than 36h past the race start, lock time ≤ now + 1 hour. Unit-tested.
      `pickDueRace` takes the earliest such race. `autoLockTeams` calls these; it does not keep
      a second copy of the arithmetic.
- [x] **Lock at creation from the calendar, not only from `config/lockState`.**
      `createTeamSecure` already locks when `liveLockState` is set (F-118). It now also locks
      when an `upcoming` race is due, stamping the same ace window `aceWindowFor` already
      defines. A team created 20 minutes before the next sweep, with qualifying already inside
      the one-hour window, is stored `isLocked: true`. Tests cover: live marker; due upcoming
      race and no marker; neither (unlocked, `canModify: true`).
- [x] **The shipped client creates through `createTeamSecure`.** `teamService.createTeam` no
      longer `addDoc`s an unlocked team. The callable's `uid` is the owner. Tests: no `addDoc`
      on the create path; `createTeamSecure` is called with `{ name, leagueId }`.
- [x] **Continuous catch-up.** When no upcoming race is due, `autoLockTeams` still stamps every
      unlocked team for the live `config/lockState` weekend (roster lock + ace window), so an
      old-app `addDoc` cannot sit unlocked through the race. It does **not** auto-fill those
      teams: a late join is locked empty and scores from the next race. Source-shape test.
- [x] A team created outside any lock window is unchanged: `isLocked: false`, `canModify: true`,
      no ace window.

## Targets
- android / ios / amazon (create path)
- functions (`createTeamSecure`, `autoLockTeams`)

## Data
No new collection. The team's existing `isLocked` / `lockStatus` fields, written by the
callable and the sweep. `config/lockState` stays the sweep's document (F-118); create does not
publish it.

## Performance budget
`createTeamSecure` adds one `races where status == upcoming` read (~24 docs) when
`liveLockState` is null. Catch-up reuses the same `fantasyTeams` collection read the sweep
already does (~40 docs) on runs with no due upcoming race.

## Out of scope
- F-021 `addedAtRace` scoring gate.
- F-044 value auto-fill at lock (forgotten seats of teams that already existed).
- Denying `allow create` on `fantasyTeams` (rules tests and F-118's forged-window create
  still use client creates; the callable is the shipped path).
- Changing ADR-001 or Pit Wall.

## Operations
- **functions-deploy** `functions:createTeamSecure,functions:autoLockTeams` after merge.
  App JS OTAs. Old binaries keep `addDoc` until a store build; the catch-up sweep covers them.
