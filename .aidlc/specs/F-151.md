# F-151 — UC: server season scope - race counts, locks, form and scoring per season

Created: 2026-11-15 · Status: implemented

## Goal

The server has no idea which season it is: "completed races" means every completed race ever, and
races are ordered by round, which restarts each season. Once the 2027 calendar is seeded (F-150)
that breaks quietly: every 2027 purchase is stamped as race 22+ (`addedAtRace`, which the app
compares with round numbers, so 2027 history hides the driver), contract lockouts run on that
all-time clock, a season lock counts 2026 and 2027 races together, auto-fill ranks 2026's last
rounds as the freshest form for most of 2027, the repair tool mixes rounds of two seasons, and a
re-approved 2026 race would score 2026 points into teams that started 2027. This must be deployed
before the season rollover runs. It also carries the owner's 2027 price rate (2026-11-15): $6 per
point, so 2027 opens at 2026's level.

## Acceptance criteria
- [x] `functions/src/season/current.ts`: `currentSeason` is `config/app.currentSeason` (set by the rollover) when it is a four-digit year; otherwise the season of the next race still to run, else of the last one run (`seasonFromRaces`). No year is written in the code. Production today: 2026.
- [x] `completedRaceCount` counts the current season's completed races. Purchases (`getCompletedRaceCount` in teamOperations.ts) and contract expiry and lockouts (calculatePoints.ts Phase 3.5) use it: one clock. Production today: 20, the same as the all-time count, so 2026 behaviour is unchanged.
- [x] The season lock counts the current season's remaining races only (teamLocks.ts).
- [x] Auto-fill's recent form is the most recent completed races by race time, not round (by round, Abu Dhabi 2026 would outrank every 2027 race). In production today the two orders are identical.
- [x] The repair tool loads the current season's completed races only (its `fromRound` is a round of this season).
- [x] Race, qualifying and sprint scoring refuse a race whose season is before the current one, with an error log line; the current and later seasons, and races with no readable season, score as before.
- [x] Race score rows (`raceScores`) carry `seasonId`, so a later app change can tell 2026's round 3 from 2027's.
- [x] `pitwallPass.js` grants the season a purchase today would (`saleSeason`, F-146), not the display season.
- [x] Rollover prices (F-150): `DOLLARS_PER_POINT = 6`, constructors 3. Dry run against production: average opening driver $159 and constructor $163 (2026 opened at $155 and $154), top driver $362 (2026: $367), lineups $185–$1815 (2026: $169–$2023).
- [x] Tests: functions 289/289 (`seasonScope.test.js` +6: the season source, past-season rule, the per-season clock against a 2026+2027 calendar, auto-fill form across the season boundary, every race-counting call site; price tests at $6).

## Targets
- server: Cloud Functions — teamOperations (addDriverSecure, swap/constructor callables), onRaceCompleted and the qualifying/sprint scorers, seasonLockTeam, autoLockTeams (auto-fill), repairTeamScoring. Functions deploy before the rollover (F-150 runbook). `functions/scripts/pitwallPass.js` (op script) and `functions/src/season/rollover.ts` (op constants) need no deploy.

## Data
No new user data. Race score rows gain a `seasonId` field.

## Performance budget
`currentSeason` is one `config/app` read; until the rollover sets `currentSeason` it also reads the
race calendar (25 documents), on purchase, scoring and season-lock calls — the purchase path already
read every completed race each call.

## Out of scope
- Backfilling `seasonId` onto the 2026 race score rows (they are all 2026; the app change that reads the field can treat a missing one as the season of its race).
- The app's own cross-season ordering (`raceScores` latest round, lockout, labels) — the app feature after this.
