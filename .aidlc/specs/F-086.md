# F-086 — UC: Round mapping misfiled race data and the reminder dedupe spammed players

Created: 2026-10-02 · Status: shipped

**This spec was written retroactively**, on 2026-10-02, after the fix shipped in #119. The work was done as a live incident response and the id was taken from the branch name without `aidlc feature add`, so the registry never held an entry for it. Recording it here rather than leaving the gap, and saying plainly that the normal order — register, spec, build — was not followed.

## Goal

Both apps, though it is registered to Undercut: the root app owns the ingestion that caused it, and Track Limits moved to its own repo the same day.

F-076 reinstated the cancelled Bahrain Grand Prix at Sepang, inserted it as R18, and renumbered the season tail so Singapore became R19 and Abu Dhabi R25. It updated `SPRINT_ROUNDS` and the seeded calendar. **It did not update `ROUND_TO_RACE_ID`**, the static round→race table in `functions/src/ingestion/config.ts`.

That table is a second, hand-maintained statement of a mapping the ingestion otherwise derives at runtime: `deriveRoundNumbers` (`functions/src/ingestion/openf1Client.ts:433`) numbers rounds by walking OpenF1 meetings that have a Race or Sprint session, in order. `deriveRoundNumbers` needed no change and got none — the drift was between the static table and the calendar it is supposed to agree with.

So OpenF1's round 18 resolved to `singapore_2026`, and Undercut's ingestion wrote Bahrain's real session times onto Singapore's race document. (I first reported those times as "corruption"; they were not corrupt, they were the right times on the wrong document.)

Two consequences, one in each app:

1. **Undercut:** qualifying and sprint results for Bahrain would have been ingested against `singapore_2026`, and Track Limits settles real garage cash against `races`. Deployed ~18h before Bahrain qualifying.
2. **Track Limits:** two race documents now carried session times inside the 24h missing-picks reminder window. `notifyMissingPicks` stored a *single* reminder stamp per user, `{ raceId, early, last }`, so a stamp written for one race did not suppress a reminder for the other, and the two races took turns clearing each other's stamp. **1,273 notifications went out, about 28 per player**, and they named the wrong race.

The dedupe bug is the one worth dwelling on: the mis-mapped data was the trigger, but a single-slot stamp can only ever dedupe one race at a time. Any future state with two races in the window would have done the same thing.

## Acceptance criteria

- [x] `ROUND_TO_RACE_ID` maps 18 → `bahrain_2026` and 19…25 → `singapore_2026`…`abu_dhabi_2026`, agreeing with the seeded calendar.
- [x] `SPRINT_ROUNDS` is `{2, 6, 7, 11, 14, 19}`, and every entry agrees with the seed's `hasSprint` flags in both directions.
- [x] A test cross-checks the static table against the seeded calendar in both directions — every round resolves to a race that exists, and every non-cancelled race is reachable from some round (`functions/test/roundMapping.test.js`).
- [x] Track Limits stores reminder state per race: `pickReminder: { [raceId]: { early, last } }`, written with `{ merge: true }` so one race's stamp cannot clear another's.
- [x] `reminderStateFor(pickReminder, raceId)` reads the new keyed shape **and** falls back to the legacy single stamp when its `raceId` matches, so players mid-window at deploy time are not re-notified from a cleared slate. A keyed entry wins over a legacy stamp on a mixed document.
- [x] A test covers the legacy stamp, the keyed map, a stamp for a different race, and malformed input (`null`, a string, a number) — `newgame/functions/test/reminderDedupe.test.js`.
- [x] Round 4 no longer maps to anything (it is left commented out at `config.ts:20`). There is one `bahrain_2026` document, not two: the reinstated race reuses it and is reached as round 18, with `round` and `status` repaired in place by `fixRaceSchedules.js`.

### What the test does not cover — read this before trusting it

The cross-check above is **weaker than it looks**, and the first draft of this spec oversold it as "the criterion that matters … a test that fails the next time they drift". Two holes, both found by the spec gate reviewing this very document:

- **It can pass vacuously.** `roundMapping.test.js:58` and `:90` do `if (!races) return;` when the seed file is missing. The seed it reads is `../../newgame/functions/src/triggers/_seedRacesData.json` — inside the `newgame/` tree that went stale when Track Limits moved to `/data/tracklimits` on 2026-10-02. **The day `newgame/` is deleted from this repo, this guard stops guarding and the suite still goes green.** It should fail loudly on a missing seed, or read a seed that lives in this repo. Tracked as follow-up below; not fixed here, because this change is a registry and spec correction and should not quietly become a code change.
- **Only the calendar half is tested.** The static table's agreement with `deriveRoundNumbers` is not asserted anywhere; it was checked by hand against the live API. It depends on OpenF1 continuing to list the cancelled Sakhir and Jeddah meetings — drop those and every round shifts by two, with nothing catching it. `config.ts:33-39` admits this dependency in a comment.

## Data

**This feature sends fewer push notifications; it collects nothing new.**

- The incident over-sent to players who had already opted into missing-picks reminders. No new recipients, no new field, and no data left Firebase beyond the push payloads themselves.
- `pickReminder` changes shape from one stamp to a per-race map on the existing user document. It holds race ids and two booleans — no personal data.
- The migration is read-compatible rather than a backfill: the legacy stamp is still honoured on read, so no write touched player documents ahead of the deploy.
- Push payloads name a race and a deadline. The bug made them name the *wrong* race, which is a correctness and trust problem rather than a privacy one.

## The standing guard — run this before a race weekend locks

The root cause was four copies of one calendar drifting apart with nothing noticing. All four are now pinned to a single fixture, `functions/test/fixtures/races2026.json`:

| copy | pinned by | runs in |
|---|---|---|
| `ROUND_TO_RACE_ID` / `SPRINT_ROUNDS` (`functions/src/ingestion/config.ts`) | `functions/test/roundMapping.test.js` | CI |
| `demoRaces` (`src/data/demoData.ts`), the app's shipped fallback | `__tests__/data/demoCalendar.test.ts` | CI |
| the live Firestore `races` collection | `functions/scripts/checkRaceCalendar.js` | **by hand, via `aidlc op`** |

The third is the one CI cannot reach, and it is the one that matters — ingestion writes it and Track Limits settles garage cash against it. **Run it before a weekend locks:**

```
aidlc op new uc-script -t "Verify the live races calendar" -p script=checkRaceCalendar.js -p backup=races
aidlc op dryrun OP-###
```

The dry run is the whole operation: the script has no `--apply` path and writes nothing. It reports round, cancellation-state and sprint-flag drift, verifies `ROUND_TO_RACE_ID` resolves to a document that agrees about its own round, checks session-time invariants (times increasing with round, no two races within 24h, sessions ordered and within five days of their race, lock keys present), and prints the next race with its lock times.

Two cautions, both learned by getting them wrong:

- It compares **cancellation state only**, not the full status. A race legitimately moves `upcoming → in_progress → completed`, and comparing status outright produced 15 false problems on the first run (`OP-105`). A check that is always red gets ignored as surely as one that never fires.
- **Do not roll back a run of it.** The `uc-script` kind takes a `backup` param, and passing `races` means the record carries `firestore-restore --only=races --write` as its rollback — a full write over production data in response to an op that wrote nothing. Passing an empty `backup` instead fails the backup step outright. Filed as aidlc#13; until it is fixed, treat these records as not rollback-able.

First clean run was `OP-106`/`OP-107` on 2026-10-03, before Bahrain-at-Sepang: 24 races matching, every mapped round resolving. One standing note it surfaced — `canada_2026` carries `fp2`/`fp3` on a sprint weekend, which that format does not run. Round 7, completed, and `getLockoutTime` reads `sprintQualifying` first on a sprint weekend, so it never affected a lock.

## Follow-up

1. ~~**Make `roundMapping.test.js` fail loudly when the seed is absent**~~ — done in #131. It now reads a fixture inside this repo and a missing fixture is a hard failure.
2. **This repo's `CLAUDE.md` does not record the coupling.** `/data/tracklimits/CLAUDE.md:19` says that Undercut's ingestion is the only writer of `races` and that Track Limits settles money against it — but that warning sits in the repo that *reads* the data, not the one that writes it. The writer is here. It belongs in both.
3. **`functions/src/seedData.ts` is a fifth calendar copy, pinned by nothing.** Still pre-renumber (Bahrain at round 4, Singapore 18, Abu Dhabi 24, no cancelled races), with full schedules and `seedDatabase()` at module scope. Nothing imports it, but running it would write `singapore_2026.round = 18` while `ROUND_TO_RACE_ID[18]` is `bahrain_2026` — this incident, recreated. The check above would catch the aftermath; it cannot prevent the run.
4. **The fixture pins less than it looks like it does.** It carries only `id`/`round`/`status`/`hasSprint`, so the CI tests do not see session times or geography — changing a timezone, or moving a race a week, passes them. The live check covers times by invariant rather than by value; the CI pair does not cover them at all.
