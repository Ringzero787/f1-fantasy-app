# F-103 — UC: the lineup lock the clients show is the one the server enforces

Created: 2026-10-05 · Status: building · Closes the open item in [F-102](F-102.md).

## The gap
On a normal weekend the app and the portal both told players lineups lock at **FP3**. The server
locks them at **qualifying** — three and a half hours later.

| | normal weekend | sprint weekend |
|---|---|---|
| `src/utils/lockout.ts` `getLockoutTime` (app) | **FP3** | sprint qualifying |
| `web/pitwall/src/lib/lock.ts` `lockTime` (portal) | **FP3** | sprint qualifying |
| `functions/src/utils/lockTime.ts` `effectiveLockTime` (**enforced**) | **qualifying** | sprint qualifying |

The server's is the one that counts: `autoLockTeams` reads `effectiveLockTime` to set `isLocked`,
and every team callable gates on that field (`assertOwnedUnlockedTeam`). So for three and a half
hours of every normal weekend the clients refused edits **the callables would have accepted**,
showed a countdown to the wrong moment, and — because `computeLockoutStatus` drives the Grid UI —
greyed out a roster the player was still entitled to change.

**Not "edits Firestore would have accepted."** An earlier draft of this spec said that, and it is
wrong in a way worth correcting rather than quietly deleting: `firestore.rules` denies owner writes
to `drivers`, `constructor`, `budget` and `totalSpent` **unconditionally**, locked or not. Rosters
only ever change through the callables. The sentence as written could be cited as evidence the
rules are permissive here, which they are not.

**Which one is right is not a toss-up.** The server's rule is principled and says so in its own
comment: lock at *the first session whose outcome scores*. Sprint qualifying is the lock on a
sprint weekend because the sprint that follows it scores. On a normal weekend qualifying scores in
its own right — `handleQualifyingScoring` awards points for it. **Nothing scores at FP3.** Locking
there was arbitrary, and it only ever took time away from players.

It is the same rule F-098 used for the ace, which is how this surfaced: deciding whether the ace
outlives the lineup lock needed a lineup lock to compare against, and the two candidates disagreed.

## Platforms and data
**Platforms:** the Expo app and the Pit Wall portal. **The server does not change** — it was
already right. No functions deploy, no rules deploy, no payload change.

**Data touched:** none. Both functions are pure and derive from `races.schedule`, which is
unchanged.

## Acceptance criteria
1. On a normal weekend both clients report the lineup lock at qualifying, and treat the roster as
   editable until then — including the window between FP3 and qualifying.
2. On a sprint weekend nothing changes: sprint qualifying, as before.
3. Both clients agree with `effectiveLockTime` in `functions/src/utils/lockTime.ts`, fallbacks
   included.
4. A weekend with no qualifying time yet has no lineup deadline rather than a wrong one.
5. F-102's ace line still appears only on sprint weekends — now because the two moments genuinely
   coincide on a normal weekend, not because the comparison routes around a known disagreement.

## What was built
- **`functions/src/utils/lockTime.ts`** — `effectiveLockTime` ends its fallback chain at
  `schedule.race` instead of null. Not cosmetic: a null deadline drops the race out of
  `autoLockTeams`'s `dueRaces` filter, so **nothing** is stamped — no `isLocked`, no `canModify`,
  no ace window — while `checkQualifyingResults` goes on scoring qualifying off OpenF1 session
  keys without consulting the document. A partially synced schedule would let a player watch
  qualifying and re-pick before the scorer ran. Locking at the race is late; null is not a lock at
  all. `aceFreezeStart` has always ended its chain there, so this is the two agreeing again.
  Found by the security read: the old client FP3 fallback had been masking it.
- **`src/utils/lockout.ts`** — `getLockoutTime` returns qualifying on a normal weekend, falling
  back to the race. The file header said "Teams lock at FP3"; it now states the scoring rule and
  records what changed.
- **`web/pitwall/src/lib/lock.ts`** — `lockTime` the same, and the private `serverLockTime` that
  F-102 added to route around the disagreement is **deleted**: `aceOutlivesLineup` goes back to
  the exported `lockTime`, because there is no longer two of anything.
- **`web/pitwall/src/lib/account.ts` and `Shell.tsx`** — the header shows `Lineups locked` when
  the team's own `isLocked` says so, whatever the countdown says. The sweep runs every fifteen
  minutes over races locking within the next **hour**, so `isLocked` goes true up to an hour
  before qualifying: with the clients no longer 3.5 hours early, a schedule-derived countdown
  alone would spend that hour promising a window the callables had already shut. Also found by
  the security read, and it is the offer-then-refuse this portal keeps being fixed for.

Players gain three and a half hours on every normal weekend. That is the fix, not a side effect.

### Installed builds stay stricter until the next release
2.4.3 is in the stores with the FP3 rule, so an installed app keeps greying the roster out early
until 2.4.4 ships. That is the safe direction — it refuses edits the server would accept, which
costs a player time but cannot cost them points — so it does not force a release. The portal is
deployed and correct immediately.

## Tests
- `__tests__/utils/lockout.test.ts` — `getLockoutTime` returns qualifying for a normal weekend;
  `computeLockoutStatus` is unlocked before qualifying, **still unlocked between FP3 and
  qualifying** (the recovered window, which is the whole point), and locked once qualifying
  starts; `lockTime` in the status is qualifying.
- `web/pitwall/src/lib/lock.test.ts` — the same for the portal, plus a sprint weekend whose sprint
  qualifying has not synced falling back to qualifying, and a schedule with only FP3 having no
  deadline at all rather than FP3.
- `web/pitwall/src/lib/aceFreeze.test.ts` — the case that used to pin the discrepancy now pins the
  agreement: on a normal weekend the lineup lock and the ace freeze are the same moment.
- `functions/test/aceFreezeStart.test.js` — `effectiveLockTime` falls back to the race, a sprint
  weekend with unsynced sprint qualifying lands on qualifying, and an empty schedule still yields
  null because there is no deadline to invent.
- `__tests__/utils/lockout.test.ts` — the same three fallbacks app-side, which the quality read
  pointed out were verified only by inspection.

Three tests asserted the old behaviour and had to change. Each is annotated with why, so the next
reader does not read the change as a regression.

## Still open
- **The app needs 2.4.4 to carry this.** Until then installed builds are early, as above. Note the
  app already ORs `lockStatus.canModify` into its UI gate, so it does not have the portal's
  final-hour problem — only the countdown it draws is early, and early is safe.
- **`formatLockStatus`'s `LOCKED · QUALI IN` branch is now dormant on normal weekends**, since the
  lock and qualifying are one moment there. It still fires on sprint weekends. Harmless, flagged
  by the quality read, left alone rather than deleted on a guess.
- **The same rule is written three times** — app, portal, functions — because they are separate
  build targets. Each carries a comment pointing at `effectiveLockTime` as the canonical one, and
  `functions/test/aceFreezeStart.test.js` plus the two client suites now assert the same
  fallbacks, which is the nearest thing to a shared test there is.
- `src/services/race.service.ts` still lists FP3 among the weekend's sessions, which is correct —
  it is a session, just not the lock.
