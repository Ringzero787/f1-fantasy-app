# F-132 — UC: Pit Wall worker watchdog and calendar check

Created: 2026-10-29 · Status: planned

## Goal

On 2026-10-29 the portal still showed "Weather · Singapore" (round 19) with the Mexico round two
days away. The worker (`pitwall-worker` on forge, which is this box) had lost name resolution to
Firestore on 2026-10-09, recovered, and then on 2026-10-11 stopped inside one tick: a Firestore
call never settled, the loop never reached the next iteration, systemd saw a healthy process, and
for eighteen days nothing was published — no projections for the USA or Mexico rounds, no
briefing, the portal and the app's Pit Wall block frozen on round 19. The stale-data self-check
lives inside the same tick, so it could not fire either. Two things fix that for good:

1. **The worker watches itself.** Every tick runs under a deadline (25 min: longer than the
   longest legitimate job, a 20-minute outlooks run plus one in-flight CLI call; the lease is no
   bound, it is renewed while a job runs), a tick past its deadline is not joined by a second one; three failed ticks in a row end the process with exit 1 so
   systemd's `Restart=always` brings it back with a fresh client. The alert on the way out has
   its own short deadline so it cannot hang the exit.
2. **A twice-weekly check, outside the worker,** says whether Pit Wall is on track and whether
   the calendar it runs on still matches the provider: worker heartbeat age, newest `pw_public`
   round and age against the registry's current round, `pw_projections` for that round, races
   that happened but are not `completed`, every upcoming race against OpenF1's meetings and
   sessions (cancelled, added, moved sessions), and the week's `pw_alerts`. It reads only, prints
   a Markdown report, files it on the share, and — when the Claude Code CLI is on the box — asks it
   for a tool-less triage of anything not OK. It is meant for cron on Monday and Thursday.

## Acceptance criteria
- [ ] `workers/pitwall/src/jobs/watchdog.ts`: `withDeadline` rejects an unsettled promise after the deadline (the timer is ref'd, so it fires even when nothing else holds the loop, and cleared when the promise settles) and passes results and rejections through; `afterTick` resets on success and returns `exit` at the third consecutive failure; pinned in `workers/pitwall/test/watchdog.test.js`.
- [ ] `serve.ts` wraps `tick()` in the deadline, counts consecutive failures, never starts a tick while the previous one is still pending, logs and exits 1 after three; `--once` and `--plan` behave as before. The deadline races rather than cancels; a job cut by the exit is handed back by its lease (documented in `watchdog.ts`). `node --test test/*.test.js` exits 0 with no cancelled test.
- [ ] `scripts/ops/pitwall-check.js` reads `pw_status/worker`, the season's `races`, the newest `pw_public`, `pw_projections`, the last 7 days of `pw_alerts`, and OpenF1 `meetings` + `sessions` for the season (two calls); the rules keep the meetings from a day before the first upcoming race onward; `pw_projections` is read with `where season == … select round`; it writes nothing; exit 1 on FAIL, 2 on WARN, 0 on OK, 3 on a collection error.
- [ ] `scripts/ops/pitwall-check-lib.js` (pure, pinned in `scripts/ops/pitwall-check.test.js`): heartbeat older than 20 min → FAIL; payload round ≠ current round → FAIL (names both); payload older than 30 h → FAIL; no projections for the round → WARN; a race 12 h past its race session and not `completed` → FAIL; a registry race with no provider meeting within 3 days → FAIL; a provider meeting with no registry race → WARN; a session moved ≥ 60 min → FAIL, less → WARN; a sprint or sprint-qualifying we list that the provider dropped → WARN; a provider session the registry lacks → WARN; alerts → WARN. (`cancelled` is handled though no writer produces it yet.)
- [ ] `scripts/ops/pitwall-check.sh` files `YYYY-MM-DD-HHMM.md` under `/mnt/smb/share/undercut/pitwall-checks/` (exit 4 when that directory cannot be written, no triage on an empty report), appends the triage only when the check is not OK and the CLI exists (scrubbed environment with only `SA_KEY` read from the ops env file, `--tools ""`, `--strict-mcp-config` with an empty MCP config, one turn, the report fenced and declared data), and exits with the check's code.
- [ ] The first live run against production reproduces the 2026-10-29 state (worker hung, payload on round 19, calendar for rounds 21–25 matching the provider) before the restart, and reads OK after the worker publishes round 21.
- [ ] No forbidden term in the report's own copy or the code (provider names pass through as data).

## Targets
- binary (the worker on forge)
- web (what the portal shows is what the check guards)

## Data
No user data. The check reads operational documents (`pw_status`, `pw_public`, `pw_projections`, `pw_alerts`) and the public race registry with the ops service-account key, and the public OpenF1 schedule. Reports hold round numbers, times and job ids only.

## Performance budget
Worker: one timer per tick. Check: six Firestore reads plus two OpenF1 calls (meetings, sessions), twice a week.

## Out of scope
- The GCP Cloud Run backup runner from the architecture note (not built; this check would show it was needed).
- Changing the race registry when the provider differs — the check reports, the owner decides.
