# F-140 — UC: Pit Wall check emails the owner on FAIL

Created: 2026-11-12 · Status: building

## Goal
The twice-weekly ops check flagged the held São Paulo result as FAIL within 30 minutes but only wrote a file and a log, so nobody knew for 3 days. Email the owner when a check FAILs (deduped, daily reminder, all-clear), and run it hourly with quiet OK runs.

The owner. The Pit Wall ops check (F-132, F-135) caught the held São Paulo 2026 result as FAIL 30 minutes after the hold (2026-11-08 19:33Z) and again on 11-09 and 11-12, each time with the exact fix, but it only wrote to `/data/scripts/pitwall-check.log` and a file on the share. Nobody reads either unprompted, so 94 teams went three days without a score (F-139). After this change a FAIL seen on two hourly runs in a row emails the owner (within about two hours of the failure, not at the next Monday or Thursday run), reminds once a day while it lasts, and sends an all-clear after two good runs in a row; a check that cannot run at all, or hangs, is mailed too.

## Acceptance criteria
<!-- Testable statements. G02 fails the spec if any is missing or untestable. -->
- [ ] A FAIL report is emailed (`new`) on the second consecutive run with the same failures; a one-run blip followed by OK/WARN is never emailed and leaves no state (scripts/ops/pitwall-alert.test.js)
- [ ] The same failures with different ages ("30 min ago", "12.0 h ago", "3.5 d ago") or a flipped registry status send nothing within 24 h of the last email and one `reminder` after it
- [ ] A different set of failures while one is outstanding is confirmed the same way, then sent as `changed`, keeping the first-reported time
- [ ] Two OK or WARN reports in a row after an alert send one `cleared` email carrying the text that was sent (not the normalised fingerprint) and reset the state; a check flapping FAIL/WARN stays one alert; a FAIL title never clears (even with no readable check line); an unreadable report changes nothing
- [ ] ✗ lines in the model-written `## Triage` section never count, and a newline or control character inside a finding's text cannot forge or hide a check line (`render` writes one line per finding)
- [ ] Email subjects contain no control characters and are at most 120 characters
- [ ] A run that cannot check (no SA_KEY, share not writable: exit 4; collection error, an empty report with any code, or a check still running after PW_CHECK_TIMEOUT (600 s): exit 3) files no empty report and is mailed as "could not run" after 4 consecutive runs; node's own warnings stay out of the reason
- [ ] With no RESEND_API_KEY/ALERT_TO the sender exits 5 (stderr + syslog `pitwall-alert`) and does not advance its state; a refused send exits 6 and does not advance it; state writes are atomic
- [ ] The wrapper's exit code is always the check's; with `PW_CHECK_QUIET=1` an OK or WARN run files no report and logs one line
- [ ] Replaying the real reports in fixtures/pitwall-reports gives exactly one `new` (11-08 19:36, the second FAIL run) and one `reminder` (11-12)

## Data
<!-- "No user data" or list every category collected, stored, or sent, and where it goes. -->
Operator data only. The sender reads `RESEND_API_KEY`, `ALERT_TO` and optional `ALERT_FROM` from the Pit Wall worker's env file (`/data/pitwall-worker/env`, chmod 600, never in the repo) — the same settings the worker's own failure alerts use — and warns in syslog if that file is readable by others. The email carries the check's failure lines (race ids, round numbers, provider status text) and goes to the owner through Resend. No player data. State (`~/.local/state/undercut/pitwall-alert.json`) holds only failure text and timestamps.
