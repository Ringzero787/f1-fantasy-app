# F-141 — UC: lock-time auto-fill never writes (constructor update assertion)

Created: 2026-11-13 · Status: building · App: Undercut (functions only)

## Goal

The lock-time auto-fill (F-044, deployed 2026-09-17) is meant to fill every forgotten seat with the best-value cars the bank affords, just before qualifying. In production it has never filled a team: no team has ever carried `lastAutoFill`. The sweep log for São Paulo (2026-11-07 17:08Z) reads `Locked 94 teams … (auto-filled 0)`, with every attempt failing with `AssertionError [ERR_ASSERTION]: Can't merge current value into a nested object`.

The cause is the write. `autoFillTeamTx` used `tx.update({ constructor: … })`. The Firestore SDK expands `update()` keys into a plain object, where `constructor` resolves to `Object.prototype.constructor`, so the SDK throws inside `commit()` before anything is sent. It does this for any value, null included. The sweep catches the error per team and locks the team as it is.

As contracts expired, rosters emptied and were never refilled:
- **Fielded rosters:** Azerbaijan 43 full, Singapore 21, USA 5, São Paulo 3 of 94.
- **Penalty:** every empty team took −25 a race.

The rest of the codebase already avoids this. `teamOperations.ts` documents the same assertion and writes `constructor` with `set(merge)`, and so does the scoring pipeline. The unit tests passed because they tested the plan and never the write.

The fix writes the fill with `set(…, { mergeFields })`. A new test pushes the real payload through the real SDK write path, offline.

## Acceptance criteria
- [ ] `autoFillTeamTx` writes the fill with `tx.set(ref, data, { mergeFields })`, built by a pure exported `autoFillWrite(team, plan, raceId)`, and never calls `tx.update`. Tested: `functions/test/autoFillWrite.test.js`, "autoFillTeamTx writes through autoFillWrite…".
- [ ] The payload for a team that needs a constructor, with `constructor` in it, passes the real `@google-cloud/firestore` write path without the SDK assertion. Tested offline against an unreachable host: "the auto-fill write passes the real SDK write path…".
- [ ] A control test shows the same payload through `update()` still raises `Can't merge current value into a nested object`, so the test can tell the two apart.
- [ ] `mergeFields` names exactly the fields written, so each is replaced whole as `update()` would have done. `lastAutoFill` is stamped with the race id and the constructor bought; `budget` and `totalSpent` are unchanged from F-044.
- [ ] A team that already owns a constructor keeps it: written back unchanged, `lastAutoFill.constructorId` null.
- [ ] All functions tests pass (`node --test functions/test/*.test.js`).
- [ ] After deploy, the next lock sweep (Las Vegas qualifying, 2026-11-21 04:00Z, sweep from about 03:00Z) logs `auto-filled N` with N > 0, and teams carry `lastAutoFill.raceId == 'las_vegas_2026'`. Verified from `firebase functions:log --only autoLockTeams` and a read-only Firestore count.
