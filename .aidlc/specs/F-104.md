# F-104 — UC: a team's leagueId has to be a usable document id

Created: 2026-10-06 · Status: building · Raised by the security read on [F-103](F-103.md).

## The gap
`db.collection('leagues').doc(id)` **throws synchronously** on an id containing a slash, and
nothing validated `fantasyTeams.leagueId`. Any signed-in player could create a team with
`leagueId: "a/b"` and reject **every** `autoLockTeams` run from that moment on — no lineup lock,
no ace freeze, for every player in the game — until somebody found the document.

It is a one-row, no-privilege denial of the control that F-095, F-098 and F-103 exist to enforce.
Nothing in the create rule covered it: that rule constrains `userId`, `budget`, `totalSpent`,
`totalPoints`, `drivers`, `constructor`, `lockedPoints` and `scoredRaces`, and stops there.

**And a create-only fix would not have been enough.** `leagueId` is not on the update rule's
denied-key list — `syncTeam` writes it on every sync — so anyone who created a team properly could
edit the field afterwards and get the same result. Both rules needed the check; the update half is
pinned by its own test, which fails against the old rules.

The same shape reaches `rankLeagueMembers` and `leagueRaceResultsWriter` off the scoring path, so
the blast radius was not only the sweep.

## Platforms and data
**Platforms:** `firestore.rules` only. No functions, no clients, no payload.

**Data touched:** none written. **Production checked before changing anything:** 77 teams — 45
with `leagueId: null`, 31 with a 20-character id, 1 with the field absent, and **none unusable**.
So the sweep was not broken, nothing needs repairing, and no migration is required.

## Acceptance criteria
1. A team can be created and updated with a real league id, with `null`, or with the field absent
   — the three shapes production actually holds.
2. A `leagueId` that `doc()` cannot take is refused on **create and update**: a slash, a relative
   path, an empty string, `.`, a reserved `__…__` name, a leading underscore, a non-string, or
   something longer than 64 characters.
3. A shipped client keeps working. `syncTeam` sends `leagueId` unchanged on every sync and must
   not start failing.

## What was built
One rules function, used by both `allow create` and `allow update`:

```
function usableLeagueId(data) {
  let id = data.get('leagueId', null);
  return id == null
         || (id is string && id.size() > 0 && id.size() <= 64 && id.matches('^[A-Za-z0-9][A-Za-z0-9_-]*$'));
}
```

Deliberately **looser than the real id shape**. Live ids are Firestore auto-ids —
`doc(leaguesCollection)` in `league.service.ts`, twenty characters of `[A-Za-z0-9]` — but pinning
the rule to that would bet on the generator and break the short ids the rules tests use. A single
path segment of word characters is the property that matters.

**The first character must be alphanumeric**, and that is how `__…__` is excluded: Firestore
reserves those ids and throws on them exactly as it does on a slash, and RE2 — what `matches()`
runs — has no negative lookahead to say "not starting with `__`" directly. `__proto__` passed the
first version of this rule and the test caught it, not me.

`null` and absent both pass: a solo team has no league, and that is most of the collection.

## Tests
`rules-tests/firestore.rules.test.js`, three cases against the emulator:
- the legitimate shapes — real id, `null`, short id, field absent — on create;
- the crashing shapes refused on create: `a/b`, `../leagues/L1`, `''`, `.`, `__proto__`,
  `__name__`, `_leading`, a number, a map, 65 characters;
- the same refused on **update**, including riding along with an innocent field, plus the two
  writes a shipped client makes (`leagueId` unchanged, and `null`) still succeeding.

**The first and third fail against the rules on master; the second passes both ways**, which is
the point — it is the regression guard for the shapes that have to keep working.

## Still open
- **The sweep keeps its own filter.** F-103 added one so a single bad row could not disable
  `autoLockTeams`; this rule stops new ones appearing, but rules do not validate data that is
  already there, and defence in depth on the control itself is worth the four lines.
- **`rankLeagueMembers` and `leagueRaceResultsWriter` are not shielded.** With the rule in place
  no new unusable id can appear and there are none today, so this is belt-and-braces rather than
  a live exposure — but they would still throw on one.
- **League *creation* lets the client choose the document id** (`allow create` on `leagues` does
  not constrain it). A slash there cannot reach Firestore, because the client SDK throws building
  the path, so it is not the same hole — noted because the next reader will wonder.
