# F-104 — UC: a team's leagueId has to be a usable document id

Created: 2026-10-06 · Merged 2026-10-06 (PR #174) · Status: implemented · Raised by the security read on [F-103](F-103.md).

## The gap
`db.collection('leagues').doc(id)` **throws synchronously** on an id containing a slash, and
nothing validated `fantasyTeams.leagueId`. Any signed-in player could create a team with
`leagueId: "a/b"` and reject **every** `autoLockTeams` run from that moment on — no lineup lock,
no ace freeze, for every player in the game — until somebody found the document.

It is a one-row, no-privilege denial of the control that F-095, F-098 and F-103 exist to enforce.
Nothing in the create rule covered it: that rule constrains `userId`, `budget`, `totalSpent`,
`totalPoints`, `drivers`, `constructor`, `lockedPoints` and `scoredRaces`, and stops there.

**And a create-only fix would not have been enough.** `leagueId` is not on the update rule's
denied-key list — `syncTeam` writes it on every sync — so anyone who created a team properly could
edit the field afterwards and get the same result. Both rules needed the check; the update half is
pinned by its own test, which fails against the old rules.

The same shape reaches `rankLeagueMembers` and `leagueRaceResultsWriter` off the scoring path, so
the blast radius was not only the sweep.

## Platforms and data
**Platforms:** `firestore.rules` **and Cloud Functions**. The rules alone were not enough — see
"The rule is not the only door" below. No clients, no payload.

**Data touched:** none written. **Production checked before changing anything:** 77 teams — 45
with `leagueId: null`, 31 with a 20-character id, 1 with the field absent, and **none unusable**.
So the sweep was not broken, nothing needs repairing, and no migration is required.

## Acceptance criteria
1. A team can be created and updated with a real league id, with `null`, or with the field absent
   — the three shapes production actually holds.
2. A `leagueId` that `doc()` cannot take is refused on **create and update**: a slash, a relative
   path, an empty string, `.`, a reserved `__…__` name, a leading underscore, a non-string, or
   something longer than 64 characters.
3. A shipped client keeps working. `syncTeam` sends `leagueId` unchanged on every sync and must
   not start failing.

## The rule is not the only door
`createTeamSecure` writes with the **Admin SDK**, so `firestore.rules` never runs on it. It
destructured `leagueId` from the callable's own data, validated only `name`, and wrote
`leagueId: leagueId || null`. Any signed-in player could therefore call the callable directly with
`leagueId: "a/b"` and land the poisoned row exactly as before — the rules-only fix was a door with
a window beside it.

Worse than a bypass of the lock sweep: such a team has `drivers: []`, which the scorer does not
skip, so the row reaches `pointsUpdates` and then `affectedLeagues`, where `doc(leagueId)` throws
and aborts the member-total sync and `rankLeagueMembers` for **every league after it in the scan**
— on qualifying, sprint and race.

Found by the security read of the rules-only version. The rules tests could not have found it:
they exercise the rules, and this path does not go through them.

## What was built
One rules function, used by both `allow create` and `allow update`:

```
function usableLeagueId(data) {
  let id = data.get('leagueId', null);
  return id == null
         || (id is string && id.size() > 0 && id.size() <= 64 && id.matches('^[A-Za-z0-9][A-Za-z0-9_-]*$'));
}
```

Deliberately **looser than the real id shape**. Live ids are Firestore auto-ids —
`doc(leaguesCollection)` in `league.service.ts`, twenty characters of `[A-Za-z0-9]` — but pinning
the rule to that would bet on the generator and break the short ids the rules tests use. A single
path segment of word characters is the property that matters.

**The first character must be alphanumeric**, and that is how `__…__` is excluded: Firestore
reserves those ids and throws on them exactly as it does on a slash, and RE2 — what `matches()`
runs — has no negative lookahead to say "not starting with `__`" directly. `__proto__` passed the
first version of this rule and the test caught it, not me.

`null` and absent both pass: a solo team has no league, and that is most of the collection.

And the same predicate in **three** more places, because a rule only guards one of the doors:
- **`functions/src/utils/leagueId.ts`** — `isUsableLeagueId`, with `LEAGUE_ID_PATTERN` and
  `LEAGUE_ID_MAX` exported so the pattern is a value a test can assert on. The rules cannot call
  it, so the expression exists twice; `functions/test/leagueId.test.js` pins the pattern string
  so the two cannot drift in silence.
- **`createTeamSecure`** rejects an unusable id with `invalid-argument` before it writes.
- **`calculatePoints`** filters every dereference through it — the three sync loops *and* the
  admin repair path, which the previous draft of this spec missed while claiming "all three".
  New bad ids cannot appear now, so this is for a row predating the guards: without it one such
  row aborts scoring for every league after it in the scan, and makes the repair tool unusable
  exactly when it is needed to clean that row up. A skipped league is logged, because the only
  other symptom would be member totals quietly drifting from team totals.
- **`teamLocks.ts`** uses the helper instead of the `includes('/')` check F-103 added. Only a
  slash and an empty string throw inside `doc()`; `.`, `..` and a reserved `__…__` name get past
  it and fail the RPC instead, which aborts the sweep just the same, one layer down.

## Tests
`rules-tests/firestore.rules.test.js`, three cases against the emulator:
- the legitimate shapes — real id, `null`, short id, field absent — on create;
- the crashing shapes refused on create: `a/b`, `../leagues/L1`, `''`, `.`, `__proto__`,
  `__name__`, `_leading`, a number, a map, 65 characters;
- the same refused on **update**, including riding along with an innocent field, plus the two
  writes a shipped client makes (`leagueId` unchanged, and `null`) still succeeding.

**The first and third fail against the rules on master; the second passes both ways**, which is
the point — it is the regression guard for the shapes that have to keep working.

`functions/test/leagueId.test.js`, seven cases. The first **reads the pattern and the bound out
of `firestore.rules`** and compares them to the exported constants. The version before it
asserted `LEAGUE_ID_PATTERN` against a hardcoded copy of itself, so loosening the rule and
nothing else left every test green — a pin that pinned nothing, caught by the security read.
Loosening the rule now fails it, which I checked by doing exactly that.

The first also asserts that `usableLeagueId` is a conjunct of **both** `allow create` and
`allow update` — because the definition agreeing with the helper is not the same as the
definition being *used*. Deleting the conjunct from `allow update` while leaving the function
intact passed every other assertion; the emulator suite caught it, but that suite is not in CI's
test command, so this has to.

The last counts the doors: three sync loops filtered, the repair path guarded and logging, the
sweep on the helper rather than its weaker inline copy, the callable validating, and
`leagueExpansion` — the final place still carrying `includes('/')`. Three rounds of this feature
shipped with a door open or a test that only looked like one, so the count is asserted rather
than remembered.

The rest:
null and absent pass; the shapes production holds pass; every shape `doc()` rejects is refused
(including a trailing newline, because RE2's `$` is end-of-text and that was worth proving rather
than assuming, plus whitespace, accented and fullwidth characters, a zero-width space and
percent-encoding); non-strings are refused; and `createTeamSecure` validates **before** it
writes. That last one is a source-shape assertion and **fails when the guard is removed**.

## Still open
- **The `leagues` create rule constrains nothing, and that is a paid-gate bypass.** A plain
  signed-in user can create `leagues/<id>` with `pro: true`, `proUntil` far in the future,
  `maxMembers: 999999` and someone else's `ownerId`. The F-068 guard only blocks `pro`/`proUntil`
  on **update**, and `pro === true` is exactly what `startLeagueTrial` checks before granting a
  Pit Wall pass trial, while `maxMembers` at creation walks around the league-expansion IAP
  entirely. Verified in the emulator by the security read. **Pre-existing, revenue-affecting, and
  bigger than this feature** — it needs its own, and it is the thing to do next.
- **A row that already holds an unusable `leagueId` is now frozen out of every update**,
  including a rename, because the check applies to the whole document. The owner can self-heal by
  writing `leagueId: null`, but no shipped client will try. There are no such rows in production.
- **The rule checks shape, not membership.** A team can still name a league the user never
  joined; it appears in that league's team list, though standings read the `members` subcollection
  so points do not leak. Pre-existing.
- **The rules suite does not run in CI.** `.aidlc/aidlc.yaml`'s G03 test command covers jest,
  the functions tests, the portal and the worker — not `npm run test:rules`. So the *enforcement*
  half of this feature, and of F-095 and F-098 before it, is covered only by a local run. That is
  the most valuable thing on this list and it is a CI change, not a code one: the script needs the
  Firestore emulator jar, and `firebase emulators:exec` wants JDK 21. **Raised with the owner.**
- **`createTeamSecure` no longer coerces `''`, `0` or `false` to a solo team.** It wrote
  `leagueId: leagueId || null`, so those became `null`; they are now `invalid-argument`. Nothing
  in this repo calls the callable — the app creates teams client-side — so no shipped client
  breaks, but it is a contract change.
- **`rankLeagueMembers` and `leagueRaceResultsWriter` take the id after the `affectedLeagues`
  filter**, so the scoring path is covered; a direct call with a bad id would still throw. An
  earlier draft of this spec claimed no new unusable id could appear "with the rule in place" —
  that was wrong while `createTeamSecure` was unguarded, which is the whole of the section above.
- **League *creation* lets the client choose the document id** (`allow create` on `leagues` does
  not constrain it). A slash there cannot reach Firestore, because the client SDK throws building
  the path, so it is not the same hole — noted because the next reader will wonder.
