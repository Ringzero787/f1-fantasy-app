# F-105 — UC: creating a league cannot hand yourself the paid features

Created: 2026-10-06 · Status: building · Raised by the security read on [F-104](F-104.md).

## The gap
`allow create: if isAuthenticated();` on `leagues` constrained **nothing**. Every field was the
client's to choose, including the ones that cost money:

| field set at creation | what it buys |
|---|---|
| `pro: true` (+ a far-future `proUntil`) | `startLeagueTrial` checks exactly `league.pro === true` before granting a **Pit Wall pass trial**. |
| `maxMembers: 999999` | the **league-expansion IAP**, which sells twenty slots at a time. |
| somebody else's `ownerId` | a league you did not make, owned by someone who did not ask. |

The F-068 guard that blocks `pro`/`proUntil` lives on **update** only — the half nobody needs to
go through. Verified in the emulator by the security read of F-104.

The `maxMembers` half had a second, quieter door: the legacy create screen (`app/(tabs)/leagues/
create.tsx`) offers 2–100 and gates it on a **client-side** credit check. That is precisely the
arrangement `applyLeagueExpansion` was written to replace — its own comment says "the client used
to write `maxMembers` itself after a purchase".

## Platforms and data
**Platforms:** `firestore.rules`, plus one validation message in the legacy app screen. No
functions change — `applyLeagueExpansion` and `passStore` already own the paid writes.

**Data touched:** none. Nothing is written or migrated. Existing leagues are untouched: the rule
is on `create`, and the owner-update rule has always allowed capacity to grow.

## Acceptance criteria
1. The shape a shipped client writes still creates a league — both screens, and the
   league-plus-owner-member batch they commit together.
2. `pro` cannot be true at creation, and `proUntil` cannot be set. Absent or explicitly off both
   work.
3. `maxMembers` must be an integer from 2 to the free ceiling (22) **at creation**. Anything
   larger, smaller, fractional or non-numeric is refused. Growth afterwards is **not** closed by
   this feature — see "What this does not close".
4. `ownerId` must be the caller, and `memberCount` must be 1.
5. The paid path still arrives: a league created free can be raised past the ceiling by
   `applyLeagueExpansion`.
6. No client offers a capacity the rules will refuse — including the legacy screen's input and
   its hint text, not just its validation.

## What was built
The create rule now requires `ownerId == request.auth.uid`, `memberCount == 1`, an integer
`maxMembers` in `[2, 22]`, and `pro`/`proUntil` absent or off. `freeLeagueCeiling()` carries the
22, mirroring `DEFAULT_MAX_MEMBERS` / `FREE_LEAGUE_MEMBER_LIMIT` in `src/config/constants.ts`.

And the legacy create screen validates against `FREE_LEAGUE_MEMBER_LIMIT` instead of 100, with a
message that says where the extra slots come from. **Without that it would be offering what the
server refuses** — the offer-then-refuse shape F-098, F-102 and F-103 were each partly about.

## What this does not close
**The expansion bypass survives in two steps.** The owner branch of `allow update` permits any
growth (`maxMembers >= resource.data.maxMembers`, no ceiling), so an owner can create a free
league at 22 and raise it to anything with one `updateDoc`. The security read reproduced that in
the emulator against this branch. `leagueService.expandLeagueCapacity` is the shipped client code
that does it.

**That is deliberate, and it is not mine to switch off.** `src/simple/grid/expansionFallback.ts`
says so in its own comment: the direct write is the fallback for when `applyLeagueExpansion` has
no verified purchase on record although the store told the device the purchase completed —
*"without that, a paying customer would get nothing"* — and *"step B removes it together with the
owner's ability to write maxMembers"*. Step B is explicitly gated on purchase validation being
proven with a real store purchase, and for league expansion it has not been. Closing the update
path today would risk a paying customer's slots to close a hole that costs the business nothing
per incident.

So this feature closes the **create** half, which has no such excuse, and leaves step B as the
owner's call. Both halves of it are one change: deny `maxMembers` on client update, and flip
`INTERIM_UNVERIFIED_EXPANSION_FALLBACK` to false.

A side effect worth knowing: `getInviteLimit` keys off `maxMembers`, so the same write also raises
the league's transactional-email allowance — bounded by `MAX_INVITE_LIMIT`, so not unbounded.

### What a paying customer loses, and does not
A player with an expansion credit used to create a larger league in one step. Now they create at
22 and apply the expansion to it, which adds its twenty slots then. Two steps instead of one; the
credit is not consumed by creation, so nothing is lost but a tap. The alternative was everyone
getting a hundred slots for nothing.

**In an already-installed build it is worse than a tap, and that is a sequencing decision.** The
legacy screen consumes the credit *before* calling `createLeague`, `pendingExpansionCredits` is a
device-local counter that nothing restores on failure, and builds in the field still offer 23–100.
So a 2.4.3 user holding a credit who creates a 42-member league after this rule deploys gets
`permission-denied` and loses the credit. Found by the security read.

The new build cannot do that — `members` is validated at the ceiling, so `needsExpansion` can
never be true and nothing is consumed — and the capacity input is gone from the screen rather than
left to be refused. But that only protects people who have updated. **Deploying the rule before
2.4.4 reaches the stores trades a narrow, unlikely credit loss for closing the hole sooner, and
that trade is the owner's to make.**

## Tests
`rules-tests/firestore.rules.test.js`, five cases. Three — Pro at creation, capacity past the
ceiling, and creating for somebody else — **fail against the rules on master**. Two pass both
ways on purpose: the shipped client shape (including the real league-plus-member batch) and the
expansion path still reaching 42. Those two are the regression guards; if the constraint is ever
tightened into breaking a real client, they are what says so.

The existing "shipped client flows" suite passes unchanged, which is the stronger signal — those
cases replay what released builds actually write.

## Still open
- **Step B: `maxMembers` on update**, above. The blocker is proving the league-expansion purchase
  end to end, not the rule.
- **`inviteCode` is still the client's to choose at creation.** `joinLeague` looks leagues up by
  code with `limit(1)`, so this is not only a collision risk — a league created with somebody
  else's code can deterministically capture their joiners. Not a paid gate and not new, but the
  security read rated it above a nuisance.
- **The create rule has no `keys().hasOnly(...)`**, so unknown fields still ride along: `ownerName`
  is spoofable, `name`/`seasonId`/`isPublic` are untyped, and `coAdminIds` is client-set. None of
  them cost money, which is why they are not in this change.
- **`memberCount` remains a client-maintained hint** on update, as F-056 already records.
- **The rules suite still does not run in CI** (`.aidlc/aidlc.yaml` G03), so this rule — like
  F-095's, F-098's and F-104's — is covered only by a local `npm run test:rules`. It is the
  highest-value thing left on this list and it needs the Firestore emulator in the runner.
