# F-093 — UC: Google sign-in on the Amazon build

Created: 2026-10-03 · Status: building

## Goal
Undercut (root app). The last hole in cross-store sign-in (F-091).

Fire OS has no Play Services, so `@react-native-google-signin/google-signin` cannot work on the
Amazon build and that build has never offered Google at all. Someone who created their account with
Google on a phone and then picked up a Fire tablet had one button — Login with Amazon — which makes
a **different** account: no team, no leagues, no Pit Wall Pass. F-091 fixed the other five
directions and recorded this one as a known gap, because it needs a browser flow rather than a
switch.

After this, every build offers every provider:

| build | offered |
|---|---|
| Amazon | Amazon, Apple, **Google** |
| Play | Google, Apple, Amazon |
| iOS | Apple, Google, Amazon |

## Acceptance criteria
- [x] The Google pill appears on the Amazon build and runs Google's web flow; everywhere else the
      native sheet is unchanged. One pill either way — a build never shows two.
- [x] The flow returns Google's **id_token**, which the app presents to Firebase as a `google.com`
      credential through the same `authService.signInWithGoogle` a phone uses. It therefore resolves
      to the **same Firebase account**, which is the whole point. A custom token would invent a
      second identity.
- [x] The authorization code never reaches the device: it is filed under `state = sha256(verifier)`
      by our own endpoint and exchanged with Google server-side, exactly as the Apple and Amazon
      flows do (`functions/src/auth/handoffStore.ts`).
- [x] **PKCE.** Google redirects by GET, so the code appears in our own Cloud Run request log line.
      The verifier does double duty — it unlocks the filed code *and* is the `code_verifier` Google
      demands to spend it — so a reader of those logs holds a code they cannot exchange.
- [x] Google's code gets its own shape check: it contains slashes (`4/0Ab…`), which the Amazon
      check rejects and which would split a Firestore path. It is only ever a field and a POST body
      parameter; the document id stays strict 64-hex.
- [x] The record is one-shot, filed with `create` so an intercepted state cannot overwrite it, and
      dead after ten minutes — all inherited from the shared handoff.
- [x] Both endpoints are rate-limited per caller and capped with `maxInstances`, like the others.
- [x] A cancellation is silent (`access_denied` → `cancelled`), and Google's own error text never
      reaches the deep link.
- [x] Without `EXPO_PUBLIC_GOOGLE_REDIRECT_URI` the pill is hidden on the Amazon build rather than
      offered and broken, so this ships safely ahead of the console work.
- [x] `providerOrder` is pure and unit-tested across every combination, including that a non-Amazon
      build never grows a second Google pill from the browser flag.

## Targets
- amazon

## Data
An authentication path, so it needs saying plainly.

- `googleAuthRedirect` receives an **authorization code** from Google and stores it in
  `auth_handoff/{state}` for at most ten minutes, then deletes it when the app collects it. No rule
  grants any client access to that collection (`firestore.rules`); it is Admin SDK only.
- `claimGoogleSignIn` exchanges that code for an **id_token** containing the person's Google `sub`,
  email and name, and hands the token to the device. Nothing is stored. The email and name land in
  the Firebase user record and `users/{uid}` exactly as they already do for the native Google
  sign-in — no new field, no new collection.
- The code appears in the redirect's own request log. It cannot be spent without the PKCE verifier,
  which is only ever in the app's memory and in the claim call's body. Nothing else is logged: the
  token exchange logs a status code, never a body.
- No change to the Play Data Safety or App Store privacy declarations: name, email address and user
  id for account creation and sign-in are already declared, and Google was already an identity
  provider on the other two builds.

## Performance budget
No new dependency — `expo-web-browser` and `expo-crypto` are already in the app. Two new Cloud
Functions, each called once per web sign-in, and only ever from the Amazon build.

## Owner steps before the pill can work
It is gated off until these are done.
1. Google Cloud Console → APIs & Services → Credentials → the **web** OAuth 2.0 client (the same id
   the native sign-in passes as `webClientId`, i.e. `EXPO_PUBLIC_GOOGLE_CLIENT_ID`) → **Authorised
   redirect URIs** → add `https://f1-app-18077.web.app/undercut/auth/google`.
2. Copy that client's **client secret**.
3. `firebase functions:secrets:set GOOGLE_OAUTH_CLIENT_ID` and
   `firebase functions:secrets:set GOOGLE_OAUTH_CLIENT_SECRET` (both prompt; the value never goes
   on a command line).
   **Do this before the next functions deploy of any kind.** A declared secret with no value blocks
   *every* functions deploy on this project, not just these two — the Stripe secrets did exactly
   that once already.
4. Put `EXPO_PUBLIC_GOOGLE_REDIRECT_URI=https://f1-app-18077.web.app/undercut/auth/google` in `.env`
   and rebuild the Amazon APK.

## Out of scope
- Using the browser flow anywhere but the Amazon build. The native sheet is better where it runs,
  and Google's branding guidance expects it.
- Linking two accounts a person already made — still the F-091 gap, and still wants a deliberate
  "connect another sign-in" from inside a signed-in session rather than a match on an email.

## Known gaps
- **Not localized**, like the rest of `src/simple/**`; belongs to the F-079 pass.
- **The pill is the same generic Ionicons glyph** as the other two, which the IP read wants replaced
  with each provider's official mark before a store review. Tracked against F-091, not fixed here.
- **No test exercises the browser session itself** — `openAuthSessionAsync`, the Custom Tab and the
  intent that carries the redirect. The guards, the ordering and the link are tested; the round trip
  is verified by hand on the Fire tablet.
