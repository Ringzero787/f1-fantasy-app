# F-107 — UC: Moonshot settlement and standings

Created: 2026-10-06 · Status: building · Design source: `docs/design/moonshot/SPEC.md` §9, §10, §18, §19, §26–§30

## Goal
Undercut (root app). When a race is finalised, every locked Moonshot on it is settled by the same scoring run that writes `raceResults`: a hit adds the reward, a miss removes the stake, a void returns the token, and none of it can happen twice. Moonshot points stay a separate, visible column so the table shows what was earned by scoring and what was earned by nerve.

## Acceptance criteria
- [ ] Settlement runs inside the existing race scoring (`onRaceCompleted` / `calculatePointsManually` / `repairTeamScoring`) after classification is final, for every `moonshots` document with `status: LOCKED` on that race. Result from the official finishing position: `WIN` P1, `PODIUM` P1–3, `TOP_5` P1–5, `EXACT_FINISH` equals target. Classification by status: finished with a position → compare; DNF and `nc` (ran, not classified — the results shape has no separate rule for it) → `dnfRule`; DNS, or a driver absent from the classification → `dnsRule`; DSQ → `dsqRule`; race cancelled → `cancelledRule`. `onRaceCompleted` never fires for a cancelled race, so `onRaceCancelled` (races `status → cancelled`) settles those — unless the race already carries a classification, in which case the flip is ignored and the calls settle on the result; un-cancelling after a void is a manual op. `nc` → `dnfRule` is a deliberate asymmetry with roster scoring (which treats `nc` like `dns`): a driver who ran and was not classified did not win, podium or finish top five — owner to confirm. Pure decision function (`settleDecision`) with tests for every rule and type. The run picks up `CONFIRMED`/`LOCKED`/`LIVE` calls (F-106 carries `lockAt` on the call rather than flipping a status), sets `status` to the result and stamps `lockedAt`.
- [ ] **Idempotent and auditable.** `settlementId = seasonId + raceId + moonshotId + settlementVersion`; the adjustment is applied in a transaction that writes `settlementId`, `officialDriverFinish`, `result`, `adjustmentAmount`, `settledAt` on the Moonshot and refuses if `settledAt` is already set. A repeated run changes nothing (tested against a stubbed Firestore: the second pass skips every call and issues no writes); the league feed entry uses the deterministic id `{moonshotId}_settled` for the same reason. `repairTeamScoring` calls settlement for every completed race before it reads the team documents, and `calculatePointsManually` re-fires `onRaceCompleted`, so both replay paths settle what a failed run left. A deleted team's call is voided on the call alone — nothing is written to the missing team. Original probability, multiplier, stake, prediction, model version and lock time are never overwritten (SPEC §27).
- [ ] **Points.** The adjustment goes to `fantasyTeams.moonshotPoints` (new, server-owned, rules deny client writes), not to `totalPoints`/`lockedPoints`; the per-race record in `raceSnapshots/{raceId}.moonshots[moonshotId]` (keyed by call, beside the scoring phases) and `leagues/{id}/raceResults/{raceId}` carries `racePoints`, `moonshotPoints`, `raceTotal` per member. Season standings order by `totalPoints + lockedPoints + moonshotPoints` (`memberSeasonTotal`, one definition with tests) at every member-total sync (race Phase 4, qualifying, sprint, repair), and the member doc carries `moonshotPoints` so the table can show the column; `maxSeasonMoonshotPointGain` caps the running positive total (`moonshotStats.pointsWon`; a hit beyond the cap is paid up to the cap and marked `capped`). Race rank and race wins stay on race points alone (`entries[].points`); `racePoints` / `moonshotPoints` / `raceTotal` ride alongside.
- [ ] **Cash.** The adjustment is applied to `fantasyTeams.budget` in the settlement transaction (the roster callables write `budget` inline the same way), never below zero (a miss larger than the bank takes the bank to zero and marks `shortfall`). A void creates no adjustment and returns the token.
- [ ] **Backfill-safe.** A race already scored before this ships has no Moonshots; the run is a no-op there. A repair replay of a race with settled Moonshots re-derives the same results and leaves the adjustments untouched.
- [ ] **League feed and history.** Settlement writes a feed entry per Moonshot (`MOONSHOT_HIT` / `MOONSHOT_MISSED` / `MOONSHOT_VOID`, SPEC §29) to `leagues/{id}/activity/{moonshotId}_settled` (new; member-read, server-write — no activity collection existed before). The "called a Moonshot" entry at lock is F-108's to post from the `moonshots` documents the league can already read after lock, and increments season stats on the team: used, hit, missed, voided, points risked/won, cash risked/won, biggest hit (a points record; cash and points are not one scale). Recap awards (SPEC §30) read these; the awards page itself is F-065.
- [ ] Standings in the app and portal show a `MOONSHOT` column when any member has one; a team's row expands to `Race Points · Moonshot · Race Total · Season Total` (SPEC §28). **Deferred to the surface features**: the app column ships with F-108 (it needs a store build anyway) and the portal column with F-109 (the portal's league document is written by the Pit Wall worker). The server data for both — `members.moonshotPoints`, `raceResults.entries[].moonshotPoints/raceTotal` — ships here.

## Targets
- firebase (functions, rules, indexes)
- android, ios, amazon and web standings columns: deferred to F-108 / F-109 (see the last criterion)

## Data
Adds server-owned `moonshotPoints` and `moonshotStats` to the team, settlement fields to the Moonshot, feed entries visible to league members. No new personal data.

## Performance budget
One transaction per locked Moonshot per race (≤ one per team), inside the existing scoring run.

## Out of scope
- Live race-day status (F-108 reads positions; settlement reads only the final classification).
- Season recap awards page (F-065 consumes the stats).
