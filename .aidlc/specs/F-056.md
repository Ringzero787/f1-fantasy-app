# F-056 — UC: Firestore rules — league member create and team list scoping

Created: 2026-09-18 · Status: planned

## Goal

The Grid security reviews found that Undercut's league documents trusted the client too much: any signed-in user could create a member document for anyone in any league (with any role, points or rank), members could rewrite their own points, rank, role and approval status, league owners could rewrite anyone's points, and any signed-in user could set a league's `memberCount` to anything or edit a league they do not own as long as they only touched that field. This feature closes those holes in `firestore.rules` **without breaking any released client** (2.2.x and 2.3.x): every write `league.service.ts` makes in those builds is replayed in an emulator test suite and must keep succeeding. What cannot be closed compatibly is recorded as a known residual and moved to F-059.

## Acceptance criteria
- [ ] `leagues/{id}/members/{memberId}` **create**: only by that user for that user (`memberId == auth.uid == data.userId`, `data.leagueId == id`), only the eight keys released clients send, `totalPoints == 0`, display name ≤ 60 chars, `rank` a non-negative integer; `role: 'owner'` only when the league's `ownerId` is the caller (`getAfter`, so the createLeague batch works); `role: 'member'` only while `memberCount < maxMembers` and with `status` matching the league's `requireApproval` setting. No server-owned field (`lastRacePoints`, `previousRank*`) can be supplied.
- [ ] Members **update**: the league owner may change only `role`, `status`, `rank` (never mint or remove `owner`; docs without a `role` field are tolerated); a member may change only their own `displayName`; nobody on a client can change `totalPoints`, `lastRacePoints`, `previousRank` or `previousRankRaceId`.
- [ ] `leagues/{id}` **update**: the owner can edit the league but not `ownerId`, and `maxMembers` cannot decrease; anyone else can only move `memberCount` by exactly one (with `updatedAt`): `+1` only as an approved member and never past `maxMembers`, `−1` only once their own member doc is gone, never below 0 (so a drifted count cannot strand a leaver). No other non-owner write is accepted.
- [ ] Write privileges inside a league (chat messages, announcement replies, invites, the `memberCount` increment) require an **approved** member (`isApprovedLeagueMember`); reads still accept a pending member because released clients detect their own pending state by querying the members list. Invite docs may carry the `expiresAt` key the legacy invite screen sends (it was being rejected).
- [ ] `fantasyTeams`: `bestRacePoints` / `bestRaceId` stay server-owned (F-054) and the queries released clients run (own teams, league teams, the global team-name uniqueness probe) still succeed.
- [ ] `rules-tests/firestore.rules.test.js` (node:test + `@firebase/rules-unit-testing`) covers every released-client flow — createLeague batch, join + count, leave + count, pending join + owner approval, promote / demote / re-rank / remove / rename / expand, standings read, own display name — and every closed hole above, plus the known residual; `npm run test:rules` runs it on the build box via `scripts/ops/run-rules-tests.sh` (starts the cached Firestore emulator jar directly because the firebase CLI wrapper requires JDK 21 and the box has JDK 17).
- [ ] Deployment is an `aidlc op rules-deploy`: dry-run attached to the PR, applied only after the owner has seen it.
- [ ] `npx tsc --noEmit` and `npx jest --ci` pass.

## Targets
- firebase (Firestore security rules)

## Data
No new user data. Narrows who can write existing league-member and league documents.

## Performance budget
Member create adds one `get`/`getAfter` of the league document; non-owner league updates add one `exists` on the caller's member document. No client changes.

## Out of scope (tracked as F-059)
- `fantasyTeams` `allow list: if isAuthenticated()` stays: released clients check team-name uniqueness with a global `where('name','==',…)` query on create and rename, so scoping `list` to own / same-league teams would break team creation until a client that asks the server instead is the minimum supported version.
- `memberCount` remains a client-maintained hint: a non-member can move it down by one (never below 0) because released clients delete their member doc before decrementing, and a member can leave and re-join to push it up towards `maxMembers`. The durable fix is a Cloud Function that owns `memberCount`.
- `maxMembers` is still written by the owner's client after a purchase; binding it to a verified entitlement needs server-side purchase validation.
- League documents (including invite codes) remain readable by any signed-in user; join-by-code depends on that query.
