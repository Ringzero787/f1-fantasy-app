# F-091 — UC: cross-store sign-in

Created: 2026-10-02 · Status: building

## Goal
Undercut (root app). An account belongs to the person, not to the store they happened to install
from — but until now the sign-in screen behaved as though it did:

| build | offered | so a person who signed up with… |
|---|---|---|
| iOS | Apple, Google | Amazon could not get in |
| Play | Google | Apple or Amazon could not get in |
| Amazon | Amazon | Google or Apple could not get in |

Someone who created an account with Apple on an iPhone and then installed the Play build was not
told their account was unreachable; they were shown a Google button, signed in with it, and got a
second empty account with no team, no league and no Pit Wall Pass. The pass is the sharp end of it:
it is a season of paid access attached to one Firebase uid.

Each build now offers every provider it can actually run, the store's own first — with one
exception added on 2026-10-03: **iOS does not offer Amazon.** That is a decision, not a limit; see
the section below.

## Acceptance criteria
- [x] The Amazon pill appears on **the Android and Amazon builds** — and only once the hardened
      Amazon flow is in that build. (It was "every build" until 2026-10-03, when iOS was dropped by
      decision; the section below carries that and the Play and Amazon builds are unaffected.)
      The reason for the gate on the flow: the original one returns Amazon's authorization code to the app on
      `theundercut://auth/amazon`, and `signInWithAmazon` exchanges whatever code it is handed for a
      session, so a code read off that redirect is an account takeover. On a Fire tablet that was a
      narrow audience; showing the same button to every Play and iOS install would have made it
      everyone. The code now never reaches the device: it is filed under the same
      `state = sha256(verifier)` as Apple's token and exchanged with Amazon server-side, and the app
      receives a Firebase custom token. `amazonWebSignInAvailable()` gates the widening on
      `EXPO_PUBLIC_AMAZON_REDIRECT_URI`, so a build made before the return URL is registered keeps
      today's behaviour rather than widening today's exposure.
- [x] The original `signInWithAmazon` callable stays, because 2.4.0 and earlier call it and cannot be
      changed. Both flows share one implementation of what an Amazon identity means
      (`auth/amazonAccount.ts`).
- [x] The Apple pill appears on the Play and Amazon builds, through Apple's web flow, and stays
      native on iOS where the system sheet exists and Apple's guidelines expect it.
- [x] The Apple web flow produces a credential that `authService.signInWithApple` hands to Firebase
      as an `apple.com` credential, so it resolves to the **same Firebase account** as a native
      Apple sign-in on an iPhone. A custom token minted from Apple's `sub` would invent a second
      identity and defeat the feature; it is not used.
- [x] The identity token never travels on the `theundercut://` redirect. On Android any installed
      app may claim a custom scheme, and an Apple identity token is enough to sign in as its owner.
      The endpoint files the token under `state = sha256(verifier)` and redirects with the state
      alone; the app trades the `verifier` — 32 random bytes that never left the device — for the
      token over HTTPS. An app that intercepted the redirect has the state and cannot derive the
      verifier.
- [x] The handoff record is one-shot (read and deleted in a transaction) and expires in 10 minutes;
      an expired record is rejected and also collected on the attempt.
- [x] The app rejects a redirect whose `state` is not the one it started with.
- [x] Apple's `error` is never echoed into the deep link — it is collapsed to `cancelled` or
      `failed`, so an unauthenticated POST cannot write query parameters of its own choosing.
- [x] A cancellation is silent on every path: no alert for `ERR_REQUEST_CANCELED`,
      `SIGN_IN_CANCELLED`, `user_cancelled_authorize`, or a dismissed browser.
- [x] Apple's one-time name (sent only on first consent) is read, length-capped, and carried all the
      way to `createUserProfile`, so a web-flow account is not called "Apple User". Over the web flow
      the name arrives beside the token rather than in the Firebase user, so it has to be passed
      through `onAppleSignIn` → the store → `authService.signInWithApple`. A malformed blob costs the
      account its name rather than the sign-in.
- [x] Both endpoints are rate-limited per caller (10 files and 20 claims a minute, keyed on a hash of
      the IP, reusing the Pit Wall handoff's window) and capped with `maxInstances`. They are
      unauthenticated writers by necessity, and a loop against one should cost a queue, not a bill.
- [x] A handoff is filed with `create` and never `set`: the design assumes an app may intercept the
      redirect and so learn the state, and with `set` such an app could replace the filed credential
      with one of its own.
- [x] `appleAuthRedirect` answers 405 to anything but POST. Apple only ever uses `form_post`, and a
      GET would put identity tokens in request logs and browser history and make the write reachable
      from an `<img>` tag. Amazon's endpoint takes GET because Login with Amazon redirects that way;
      its code is worthless without the client secret, which is only ours.
- [x] `cleanupAuthHandoffs` sweeps daily, for the sign-in abandoned at the consent screen that
      nobody ever came back to claim.
- [x] Which pills a build shows, and in what order, is a pure function
      (`src/simple/grid/signInProviders.ts`) and is unit-tested across every combination. It decides
      whether a person reaches their account or quietly makes a second one, and it previously lived
      in a render block as three nested conditionals.
- [x] Without `EXPO_PUBLIC_APPLE_SERVICES_ID` the web pill is hidden rather than offered and broken.
- [x] The validators and the deep-link builder are pure and unit-tested with no Firebase runtime
      (`__tests__/auth/handoffGuards.test.ts`), including traversal and injection attempts on the
      state.

- android
- ios
- amazon

## Data
**This feature is an authentication path**, so it needs saying plainly.

- `appleAuthRedirect` receives, from Apple, an **identity token** (which contains the person's Apple
  `sub`, and their email — possibly a private relay address) and, on first consent only, their
  **chosen name**. It stores the token and the name in `auth_handoff/{state}` for at most ten
  minutes and deletes the record when the app collects it. No rule grants any client access to that
  collection; it is reachable only through the Admin SDK.
- The identity token is handed back to the device, which presents it to Firebase Auth. The email and
  name land in the Firebase user record and the `users/{uid}` profile exactly as they already do for
  a native Apple sign-in on iOS — no new field, no new collection beyond the ten-minute handoff.
- Nothing is logged but failure messages. The token is never printed; `console.error` carries only
  the Firestore error's message.
- Login with Amazon being offered on the Play and iOS builds collects nothing new: the same Amazon
  profile fields (`user_id`, `email`, `name`) as on the Fire tablet. What changes is where the
  authorization code is spent — on the server rather than on the device. `auth_handoff` holds that
  code for at most ten minutes, under the same rules as Apple's token.
- `.aidlc/data-safety.yaml` is updated: the `email` entry said "Google / Apple sign-in", and Amazon
  is now an identity path on all three stores.
- No change to the Play Data Safety or App Store privacy declarations: the categories (name, email
  address, user id) and the purpose (account creation and sign-in) are already declared for Google
  and Apple sign-in.

## Performance budget
No new dependency — `expo-web-browser` and `expo-crypto` are both already in the app. Two new Cloud
Functions, each called once per web sign-in. The Apple web flow costs one browser session and one
callable; the native paths are unchanged.

## Out of scope
- **Linking two existing accounts.** Someone who already made a Google account on Play *and* an
  Amazon account on a Fire tablet still has two. This feature stops the fork happening again; it
  does not merge what already forked. See Known gaps.
- **Google sign-in on the Amazon build.** Fire OS has no Play Services, so the native module cannot
  work there and the Amazon build does not link it at all. The same web-flow shape would do it —
  `handoffStore.ts` already takes a `provider` — but it is a separate change. Someone who signed up
  with Google and only has a Fire tablet still cannot reach that account; Apple is their way across,
  which is why the Apple pill is on the Amazon build too.
- Email and password registration (`app/(auth)/register.tsx` exists and is unreachable by design —
  the screen says "NO PASSWORDS. YOUR ACCOUNT IS YOUR SIGN-IN").
- Choosing which provider a new account is created under, or showing the person which provider they
  used last.

## Owner steps before the Apple pill can work
It is gated off until these are done, so the build is safe to ship first.
1. Apple Developer → Certificates, Identifiers & Profiles → **Identifiers** → new **Services ID**
   (suggested `com.undercut.app.signin`), enable Sign in with Apple, Configure:
   primary App ID `com.undercut.app`; **Domains** `f1-app-18077.web.app`; **Return URL**
   `https://f1-app-18077.web.app/undercut/auth/apple`.
2. Download the `apple-developer-domain-association.txt` Apple offers, put it at
   `public/.well-known/apple-developer-domain-association.txt`, deploy hosting, then press Verify.
   (`firebase.json`'s hosting `ignore` no longer excludes dotted paths, so the file publishes.)
3. Firebase Console → Authentication → Sign-in method → **Apple** → add the Services ID.
4. Put `EXPO_PUBLIC_APPLE_SERVICES_ID=<the Services ID>` in `.env` and rebuild.

## Owner steps before the Amazon pill leaves the Amazon build
Also gated off, for the same reason.
1. developer.amazon.com → Login with Amazon → the Undercut security profile → **Web Settings** →
   add `https://f1-app-18077.web.app/undercut/auth/amazon` to **Allowed Return URLs**. Leave the
   existing `https://www.humannpc.com/undercut/auth/amazon` in place: builds already installed use
   it.
2. Put `EXPO_PUBLIC_AMAZON_REDIRECT_URI=https://f1-app-18077.web.app/undercut/auth/amazon` in `.env`
   and rebuild. Until that line exists the pill stays on the Amazon build and the old flow runs
   there, exactly as it does today.

## Deploy order
functions → hosting → rules → builds. A build whose endpoints are not deployed cannot sign anyone in
through them, and the Hosting rewrites are what give Apple and Amazon a URL to return to.

## iOS does not offer Amazon
Decided 2026-10-03, after the matrix was complete. Login with Amazon is a browser flow and runs on
iOS perfectly well, so this is the one provider left out by choice rather than capability: the App
Store audience has no reason to hold an Amazon identity, and a third third-party button earns its
place less there than the reach it buys.

The cost, stated in the same terms as the Goal above rather than as a reachability footnote: **this
one direction keeps the silent account fork.** Someone who signed up with Amazon on a Fire tablet
and then installs on an iPhone is not told their account is out of reach — they are shown Apple or
Google, use one, and get a second empty account with no team, no league and no Pit Wall Pass. The
pass is the sharp end: a season of paid access attached to the uid they can no longer reach, and
there is no merge path (see Known gaps).

Two things that bound it. No released iOS build has ever shown the Amazon pill, so this is a gap
that was never closed rather than one that was opened — nobody is losing an account today. And
reversing it is one line in `providerOrder` plus a build.

Every other direction works, once the owner steps above are done — until the Services ID and the
return URLs exist, the Play build still offers Google alone.

## Known gaps
- **An Amazon account cannot be reached from an iPhone.** By decision, not capability — see "iOS
  does not offer Amazon" above. It is the one direction of the matrix that still forks silently.
- **Two accounts already made cannot be merged.** `signInWithAmazon` creates `amazon:<user_id>`, and
  when the Amazon email already belongs to another provider's account it creates the Amazon one
  *without* an email instead of linking. Linking on a matching email is a takeover vector unless the
  email is known-verified, so the honest fix is a deliberate "connect another sign-in" action taken
  from inside an already-signed-in session, not an automatic merge at the sign-in screen. Not built.
- **No Google on Fire OS**, as above.
- **Not localized.** The pill labels are English, like the rest of `src/simple/**`; they belong to
  the F-079 pass.
- **Stale handoff records are collected lazily**, on a later claim of the same state, which never
  comes for an abandoned sign-in. A Firestore TTL policy on `auth_handoff.expiresAt` would sweep
  them; until then a handful of ten-minute-dead documents can accumulate.
- **No test covers the browser session itself** — `openAuthSessionAsync`, the Custom Tab, and the
  intent that carries the redirect. The guards and the link are tested; the round trip is verified by
  hand on a device.
