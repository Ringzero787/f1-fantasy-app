# F-154 — UC: season rollover rehearsal and hardening before the production run

Created: 2026-11-17 · Status: planned

## Goal

The rollover op (F-150) is merged and has never run in full: its first complete execution would be the production one, after which teams are reset. It also writes its groups in the order teams, leagues, prices, calendar (`functions/src/season/rollover.ts`), so for the length of the run a reset team can buy at 2026 prices. This feature proves the op off production first and closes the gaps that a rehearsal would otherwise only find live.

Source: the 2026-11-17 EGM review of 2027 readiness (finding R-05); the evidence lines were re-checked against `origin/master` on that date. Dates are proposals worked back from the 2027-03-14 opener, not owner decisions, unless marked.

## Acceptance criteria
- [ ] The rollover is run with `--apply` against a copy of production **in the Firestore emulator** (not a second cloud project: a copy with real push tokens and deployed functions could message real players), then run again after an induced mid-run failure, then rolled back; each of the three ends in the state the F-150 runbook describes, and the result is written into the F-150 spec.
- [ ] How the rehearsal is made possible is written down and safe: the script is pinned to the production project and refuses while any 2026 race is open, so the copy is doctored (the remaining races marked completed and settled) and the script is pointed at the emulator through an explicit, tested switch that cannot reach production. The production-project guard is asserted on the rehearsal path.
- [ ] Because the 2026-12-04 rehearsal runs on doctored data, a second dry run on the real, finished season is read on the day of the rollover before `--apply`.
- [ ] A 2.8.0 app build and the portal are pointed at the rolled-over copy and the Team, Market, League and Pit Wall screens are checked. 2.8.0 is what players run from the rollover until the 2027 build is forced, so there is a pass bar: no crash, no screen that invites an action the server refuses, no 2026 result shown as current. Anything that fails goes to F-155 before the rollover runs.
- [ ] Prices are written before any team is reset, or roster and market writes are locked for the run; a test pins the order or the lock.
- [ ] The op refuses to run while any completed 2026 race lacks its `raceScores` rows, and while any 2026 Moonshot is not in a terminal state. The existing preconditions live in the script (`functions/scripts/seasonRollover.js`), not the pure planner, so these two are either moved into a pure, tested function or tested through the script against the emulator.
- [ ] The backup path list is a file the op reads, not a parameter pasted from dry-run output.
- [ ] The runbook in F-150 names a point of no return and what "fix forward" means after it.
- [ ] It is confirmed, and recorded where, that a project-level Firestore export or point-in-time recovery exists; if not, one is taken before the run. Where that export is stored and how long it is kept is written down, and the same for an Auth export if one is taken.
- [ ] It is confirmed that F-150's own prerequisites are live before the run: the functions deploy carrying `onUserDeleted` and the `seasons.memberUserIds` index (recorded as OP-229 and OP-227; check the live project, not the record).
- [ ] What the rollover does to Track Limits, which reads `races` and `drivers` in the same project, is written down after reading its code.
